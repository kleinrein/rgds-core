# RG DS Impeccable

The DS performance benchmark of RG DS OS: an original ROM that holds DSCore to a score out of 10000. Only 10000 is
called **IMPECCABLE**, and it is meant to stay out of reach, so the number always says how far there is to go. Other
systems get their own ROMs later, with the same rules.

```sh
make impeccable        # build/impeccable/Impeccable DS.nds
```

Copy the ROM to the games folder and start it like any game: **A** runs everything, **START** runs the 1x tests only.
Leave the handheld alone and on the charger while it runs. The game restarts itself when a test needs other settings.
Results stay on screen (L/R for each test) and in `userdata/bench/impeccable-ds.jsonl`, one line per test.

## How a ROM can measure this

A DS program only sees emulated time: its timers read the same at 10 fps as at 60. So DSCore gives this one cart
(title `RGDS IMPECC`, code `RGIM`) a small port at `0x04FFFB00` (`dscore/src/core/io/bench_port.h`). The ROM opens and
closes measuring windows and asks for settings; the frontend answers from its clock and the panels' page flips
(`dscore/src/frontend/sdl/bench_recorder.h`). On anything else the ROM says it needs DSCore.

Settings go through the same `game.ini` and restart as the game menu (`GameMenu.poll_bench`), so a test runs what a
player gets: the right binary, the right display path, and adaptive resolution off, because falling back to native is
not a way to pass. Progress is kept in `userdata/bench/impeccable-ds.bin`, so a run survives each restart.

## The tests

Every scene is generated by code and seeded, so all runs see the same frames. CPU scenes keep the ARM9 busy to line 172
of 192, so idle skip cannot flatter them. Each CPU kernel's result is checked against its right answer, worked out
natively at build time; divides, square roots and rewritten code are checked too. A wrong answer scores the test 0.

| Test | What it pushes |
| --- | --- |
| PACE | Almost no work: the display path alone, 30 s. A band and a ruler step every frame, so a drop shows on camera too |
| ARM9 | The CPU kernels, ARM and Thumb, plus the divider and square root units |
| JIT CHURN | 24 KB of code rewritten and run every frame, as overlays force on a recompiler |
| ARM7 + SPU | All 16 sound channels and a busy ARM7, against a busy ARM9 |
| 2D STORM | Both engines: all layers, 128 rotated blended sprites, per-line scroll by HBlank DMA, windows, an HBlank interrupt |
| 3D GEOMETRY | 1922 textured triangles lit by four lights, through GX FIFO DMA |
| 3D FILL | 12 full-screen translucent fogged layers, edge marking, anti-aliasing, a shadow volume. This is what scale costs |
| TEXTURE CHURN | 96 KB of textures streamed and a palette rewritten every frame |
| STATE SPIKES | A state not seen before every 20 frames, where a renderer building shaders on first use stalls |
| DUAL 3D | 3D on both screens, a frame each in turn, held by display capture |
| CAPTURE LOOP | Last frame's capture read back as this frame's texture |
| GAUNTLET | All of it at once |
| 2D SHOWCASE | Flat-coloured art with every kind of edge, scrolling, and next to no other work |

The same scenes then run with **HD** and **HD smooth** (`rgds_2d` 4 and 5, on Showcase and Gauntlet), nine **shaders** (on
Showcase, where the shader is the cost: on the Gauntlet they all read as the Gauntlet), **3D at 2x-5x** (Geometry, Fill,
Gauntlet) and **fast forward** (the player's own, uncapped).

A test stops at a quarter over its planned time, however few frames that was: scores read rates, and at 5 fps a fixed
count would take minutes. Each line of the log carries the time, a hash of the engine binary and the release.

Bezels are not tested here: DSCore has none, they belong to RG DS Play, so they come with the GBA ROM.

## Baseline

Version 2, 2 November 2026, RG DS on charge, starting at 50°C, OS release `0.8.0-d69a9cd51aa8-os8dc0becf`: **402**. Core 1x
995, 3D 2x-5x 19, HD filters 217, shaders 1796, fast forward 569. A full run took 13 minutes. One run only: how far runs
differ has not been measured.

Version 3 waits for VBlank on the interrupt, as games do, not by reading VCOUNT, which cost about 6 ms of every frame: the
idle-loop skip can't take that register, so version 2 scored the ROM's own wait. Three rounds each on the handheld, on the same engine:

| | Version 2 | Version 3 |
| --- | --- | --- |
| Pace, uncapped | 79 fps | 164 fps |
| Pace, work per frame | 12.3 ms | 6.1 ms |
| Pace, score of 1000 | 249-382 | 340-379 |
| 2D Showcase, uncapped | 79 fps | 164 fps |
| 2D Showcase, score of 1000 | 283-285 | 420-427 |

Missed refreshes did not change: Pace 9-17 and 17-19 in 30 s, 2D Showcase 6 in 12 s in all six runs. They don't come from
the frame's work. No full run of version 3 yet, so 402 is still the last total.

## The score

`bench/ds/score.h` is the whole of it. A paced test is out of 1000, the product of:

- **smooth**: 0.90 per missed refresh, per 15 seconds. One miss costs a tenth; ten leave a third.
- **hitch**: 0.95^((g-1)²) for the longest gap of g refreshes.
- **speed**: (achieved / 59.83 fps)⁴.
- **headroom**: the scene again with the brakes off: 120 fps or more 1.0, 60 fps 0.5, below that 0.5 × (fps/60)².
- **sharp**: (share of frames on the GPU raster)¹⁶ at 2x-5x.
- **audio**: 0.97 per underrun, per 15 seconds.
- **latency**: the 99th percentile from swap to flip: 8.3 ms or less 1.0, in a line down to 0.5 at 33.3 ms and beyond.

Holding a flawless 60 with nothing to spare is 500. That is deliberate: a real optimisation must always move the score,
even when the game already looks perfect. Fast forward is log2(speed) / 3, so 8× is full marks.

Under that product sits a **climb**, 2% × (fps/60)² of full marks, so going from 4 to 8 fps counts even where the product
is nothing. A wrong or unapplied test scores 0, floored at 0.01% in the total.

The total is the weighted **geometric** mean: one weak test sinks the run and nothing can buy it back. 9999 is the most
anything short of a perfect run can show.

Scores compare only within one `BUILD_VERSION` (`bench/ds/main.c`). Bump it whenever a scene or rule changes.
