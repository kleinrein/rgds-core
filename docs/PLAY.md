# RG DS Play

RG DS Play (`play/`) is the player for every system that isn't the DS. It starts with the Game Boy Advance, Game Boy and Game Boy Color, and with the thing that makes it belong on a two-screen handheld: the **companion screen**.

The game runs on the top panel. The bottom panel shows the game's own map, kept up to date while you play, the way the DS Castlevanias and Metroid Prime Hunters use their second screen. Or it takes the game's HUD off the game screen, the way Mario Kart DS does: in Mario Kart: Super Circuit the laps, time, the top four and a large course map move to the bottom panel. Games without a companion profile show a title card on the bottom panel and play as usual on the top one.

> **Status, 23 October 2026: in RG DS Core, behind an option, not released.** GBA, GB and GBC games launch from the launcher through RG DS Play with the shared in-game menu (Settings → Library → Systems → All systems, off by default). It runs on the owner's RG DS as a side-by-side test release (`tools/play_device.py install`); no public package or update carries it yet. Mario Kart: Super Circuit (Europe) has been hand-played on the handheld.

## In RG DS Core

Other systems behave like DS games: the same library, the same in-game menu, the same saves and statistics. Everything that differs by system lives in one place in each layer, so a new system plugs into the same path.

- **Systems** (Settings → Library, first row, DS only or All systems; `show_systems` in `ui.ini`, off by default). Off: Home and the DS library are exactly as before, and other systems' folders are not even scanned. On: Home's **Games** opens **Systems**, one DSi-style card per system with games (the DS first, then Game Boy Advance, Game Boy Color, Game Boy) and its game count. A card opens that system's games in the usual Cartridges / Covers / List views; Back returns to Systems, then Home. **Favourites**, **Recents** and **Last played** span every system.
- **System icons:** every system has its own drawing instead of a shared cartridge, in the icon style the theme uses: the generated artwork (Rich) or the hand-drawn 16×16 mask (Simple pixel). The set covers every system of the stock Anbernic Linux card, so a system that RG DS Play opens later already has its icon. See [the icon set](../assets/systems/README.md).
- **The two-screens mark:** a game that RG DS Play gives a second screen of its own (a map, the team, the HUD) carries a small chip with two stacked screens in the bottom-left corner of its cover on the games screen, mirroring the favourite heart in the top-right. It has no text, so it needs no translations, and it is drawn on the selected game's cover only, not on the small tiles of the carousel. The launcher finds the games from the companion profiles themselves (`src/launcher/dual_screen.hpp`): a Game Boy or Game Boy Color cart is found by its maker code or, for the older carts without one, by its header title; a Game Boy Advance cart by its code; a zipped game cannot be opened to see its header and shows no mark.
- **Where games are found:** the stock card's `Roms/GBA`, `Roms/GBC`, `Roms/GB` and `rgds/games/gba|gbc|gb` (both cards), passed by `runtime/session.py` (`system_roots`) as `--system-dir`. A `gba` folder inside a DS folder is left out of the DS list.
- **Which engine:** chosen from the game's system wherever it is started (library, Last played, game switcher, a restart): `runtime/play_options.py` `engine_for()`. DS games keep their DS engines; `rgds-play` is appended to the engine list (stored indexes keep their meaning) and is never offered as a DS engine.
- **The in-game menu** is the shared one: Resume, Save and Load (the checkpoint gallery with pictures), **Graphics**, Emulator (FPS, fast-forward, power profile, Save & restart, Reset state; the DS-only rows are unavailable), Sound, Brightness, Controls, Game switcher, Return home. The bridge drives the player like any SDL engine: F5 saves the machine to the state slot, F7 loads it, Tab toggles fast-forward, quitting saves first when auto-save is on. Auto-load, quick resume, lid sleep, volume keys and playtime come from the runtime as for every engine.
- **Graphics** for RG DS Play: **Game screen** (Sharp fill · Whole pixels · Smooth fill), **Second screen** (Companion · Info screen · Off · Swap screens: the Info screen is the title card every game without a second screen of its own shows, with the corner button for the controls, see [COMPANION.md](COMPANION.md)) and **Bezel** (Off, the game's own machines, then the owner's picture bezels; see Bezels below; the code and `play.ini` still call it `frame`), applied live through the bridge (`play-graphics:<fit>:<second>:<frame>`, the player's exported `rgds_play_set_graphics`) and kept per game in `library/<key>/play.ini` once the player confirms; and **Shader**, the same carousel and presets as the DS engines.
- **System defaults** (Settings → Library → System defaults, `userdata/system-defaults/<system>.ini`; `runtime/play_options.py`) are what every game of a system shares until a game says otherwise: **Game screen**, **Second screen**, **Bezel**, **Shader** and, for the Game Boy and Game Boy Color, **Screen colours**. A game's `play.ini` holds a key only where it differs from its system's default, so picking the default again means following it; the in-game Graphics page marks the default choice, shows `Default (…)` on a row that follows it, and ends with **Save as system default**. The shader resolves game choice, then the system default (`filter=`), then the system's own screen (GBA, GB, GBC), then Settings → Library → Default shader (DS games only).
- **Screen colours** (Graphics, last row; `play/src/ui/colour.cpp`, the list in `play/src/ui/gb_palettes.hpp`) is the handheld a Game Boy game is shown on. It is a colour step on the picture just before it is drawn, not a shader: it looks at one pixel at a time, so it also works on the direct KMS present, where the bridge's filters do not run. An original **Game Boy** game gets **Game Boy** (the default: the first handheld's green) · **Game Boy Pocket** · **Game Boy Light** (shades after SameBoy's measured palettes) · **Game Boy Color** · **Black and white**: its four greys take that screen's four colours. **Game Boy Color** is the colour handheld's own colours for the game: its boot ROM picks palettes for the background and both sprite sets by the cartridge header (the table mGBA carries, and the boot ROM's white, green, blue default for a game it does not list); the core draws them (`play/src/core/mgba_gb.c`, live, no restart), then the Game Boy Color screen correction below. Every Game Boy game plays on a handheld: a Super Game Boy cartridge (Pokémon Red and Blue, Wario Land II) runs as a plain Game Boy, so these screens apply to it (an older save state made in Super Game Boy mode is turned back into a Game Boy when it loads). A game that runs on the **Game Boy Color** (a `.gbc`, or a `.gb` made for both, flag 0x80 in its header, such as Pokémon Yellow) gets **Game Boy Color** (the default) · **Game Boy Color, darker** · **Full colour**: the screen's channel mixing (the weights Gambatte made common) that tames raw RGB555 on a modern panel, applied through a 32,768-entry lookup table; Full colour is the raw values. Game Boy Advance games keep the GBA screen shader's colour response. The emulator, the companion's probes and the HUD split see the game's own greys (except Game Boy Color colours, which the core draws), because the step runs on a copy. Applied live through the bridge (`play-color:<palette>:<correction>`, the player's exported `rgds_play_set_color`), kept per game in `library/<key>/play.ini` (`palette=`, `colour=`) and passed to the player as `--palette` / `--colour`. The companion screen's own drawing (a map, the party) is not coloured.
- **Bezels** (`play/src/ui/frame.cpp`, called frames in the code) are drawn by the player from shapes and the launcher's font, with no pictures of real consoles. Each system is offered only its own machines (the in-game menu is told the system by the runtime, so a zipped game gets its own bezels, not the Game Boy Advance's): one list, `play/src/ui/frame_styles.hpp`, read by the player and the launcher's Bezel picker, with `runtime/play_options.py` `FRAMES` repeating its names and systems (a test compares). A frame kept for another system's game (an old GBA shell on a Game Boy game) falls back to Off, unless the owner has a picture of that name in the game's own frames folder.
  - **Game Boy**: the original (warm grey body, slate bezel with its big low-right curve, the game in its own dark window, the red and blue lines with DOT MATRIX WITH STEREO SOUND over it, the red power light with BATTERY under it, GAME BOY in the logo's slanted lettering under the bezel), also in the Play It Loud colours (Red, Yellow, Green, Blue, Black); and the **Pocket** in Silver, Black, Yellow, Red, Green, Blue and Pink (a slim dark bezel with even corners, GAME BOY pocket under it). The game as large as the bezel leaves room for (about 2.4×).
  - **Screen only** for the Game Boy, the Pocket and the Color: just the bezel, edge to edge, so the game fills the panel at exactly 3× (480×432, whole pixels) with the window, the power light and (Game Boy, Color) the lines or the name around it.
  - **Game Boy Color** in Berry, Grape, Kiwi, Dandelion, Teal and Atomic Purple (clear, its insides showing): a black bezel with the power light and GAME BOY COLOR under the screen, COLOR a colour a letter.
  - **Game Boy Advance** in Indigo, Glacier, Black, Platinum, Arctic, Fuchsia and Spice: the AGB whole at 2x, its shell filling the panel with the low corners rounded off, L and R in the top corners, the dark lens with GAME BOY ADVANCE under the screen, the pad and green light on the left, A and B on the right, SELECT and START and the speaker's holes below.
  - the **black bar**, for the Game Boy Advance only: the game across the full width at the top (640×427, like Sharp fill) and GAME BOY ADVANCE on a black bar below, ADVANCE in a violet-to-pink sweep; the layout spruceOS uses with the "Perfect" overlays. A `frame=bar` kept for another system's game falls back to Off, like any frame of another system.
  - **Home consoles** draw the machine's own front on the rails beside the game and the bands above and below it, with the game as large as a 40-pixel rail allows, in quarter steps (a 256-wide game at 2x, a 320-wide one at 1.75x, the C64's 384 at 1.5x on a 32-pixel rail). NES: pale grey over dark, its ridges and door seam, POWER and RESET, the sockets with their pins. SNES: two greys, sliders, the four coloured buttons. Mega Drive: gloss black, the round dish of its cartridge door with moulded rings and a gold rim, 16-BIT. Master System: the white grid and the red band. PlayStation: pale grey, Open, the four shapes. Nintendo 64: charcoal, the stick, C buttons. ZX Spectrum: rubber keys and the rainbow corner. Commodore 64: beige, brown function keys, the rainbow badge. Other stock systems have a plain front in their colours with the name along the rail, ready for when RG DS Play runs them.
  - **Handhelds held sideways**: the **Game Gear**, the **Neo Geo Pocket Color** (Silver, Black) and the **WonderSwan Color** (White, Blue) are whole on the panel with their controls beside the screen. The **PSP** keeps the game at full width, SONY over it and its row of small buttons under it. TVs, the PC monitor (also for ScummVM) and the arcade cabinet stay as they were, for the systems they suit. A system with no machine of its own to draw, such as Game & Watch, offers only Off.
- **Picture bezels** are the owner's own: any PNG in `userdata/frames/<system>/` (`gba`, `gbc`, `gb`) is offered by its file name after the built-in bezels. They are laid over the game like RetroArch overlays (640×480 or any size, scaled to the panel), and the game fills their see-through part (alpha below half), which is left fully clear (an LCD grid an overlay draws there is dropped, so the Shader setting alone decides the screen's look), so the 640×480 overlays made for the Miyoo Mini and RG35XX fit as they are. None are shipped: the ones spruceOS uses, the "Perfect" overlays (`ourigen/perfect_overlays`, after 1playerinsertcoin, with bezels by mugwomp93 and drkhrse), carry no licence and Nintendo's logo, and libretro's MIT `overlay-borders` has only 16:9 photographs of the console. Frames go through `play-graphics` by name; the bridge takes the rest of the command line, so names may hold spaces.
- **Shaders** run in the bridge's GL pass as for the DS: it also takes 240×160 and 160×144 textures from `rgds-play`, and compiles the presets that draw an LCD grid with the game's own grid instead of the DS's 256×192, so each cell is one GBA or Game Boy pixel. While a shader is chosen the player draws its game texture plainly (no render target, the bridge's `rgds_shader_live`), so the pass can take that draw and do the scaling. The second screen is never shaded: the companion and the Info screen are the player's own interface in the launcher's look, and like the launcher they keep their pixels (only the game picture is filtered).
- **GBA screen** (preset 30) is what a GBA game shows while its own shader is Default: the GBA LCD's colour response (after Pokefan531's public-domain GBA model: a darker gamma, colours bleeding into each other, slightly lower brightness; darkened half as much as the unlit AGB-001 screen, since the RG DS panels are lit) and the faint gaps between its pixels, one cell per GBA pixel. **GBA Color** (29) is the colour alone. **GBA true colour** (33) is the full-strength correction for players who want the colours the artists drew for: GBA games were painted pale and washed out so they would read on the dark, unlit AGB-001 screen, and look faded on a modern panel; this preset follows the GBA colour model Talarubi and Near measured for higan (the LCD's 4.0 gamma against the panel's 2.2, the channels' bleed, slightly cool whites), not halved. **GBA true screen** (34) is that colour with the same faint pixel gaps as GBA screen. All four sit in the carousel's GBA screens group. **Game Boy screen** (31) is a Game Boy game's Default: the original dot-matrix LCD, whose gaps show the lighter backing (most of all on dark areas; on light areas gaps and pixels are the same colour) and whose dark pixels cast a faint shadow down and to the right. **Game Boy Color screen** (32) is a Game Boy Color game's Default: its faint pixel gaps. Neither changes colour: Screen colours does. A game of another system is offered only the Original presets (Off, Sharp bilinear) and its own system's screens; the other looks (DS screens, Natural, Vivid, Pixel art, Moods) were drawn for the DS picture and stay with DS games, and a DS game is offered no other system's screens. `runtime/play_options.py` (`shader_for`) keeps the same rule at launch: a GBA or Game Boy game whose choice is Default, or a look made for the DS, gets its own screen.
- **Windows:** the player gives its two windows the launcher's Wayland roles (`org.rgds.top`, `org.rgds.bottom`), so Weston puts the game and the companion on their own panels.
- **Two GL contexts, one thread:** each panel has its own window, renderer and GL context. On the RG DS (Mali, Wayland) SDL's idea of the current context drifted from EGL's, so the companion's texture uploads landed in the game window's context and the bottom panel kept its first picture (the title card, or the first HUD) for a whole race. The player now binds a panel's context for real (released, then made current) before touching it, and draws and presents each window in one go (`use_panel` in `play/src/frontend/main.cpp`). Verified on the handheld from the display controller itself, through RG DS Core's own launch, a race, the game menu and back.
- **Seeing what the panels show:** renderer readbacks and the bridge's capture read an app's own buffers, which hid this bug. `tools/scanout.c` reads the planes the display controller scans out (after Weston), so it shows exactly what is on each panel; build and run it as its header says.
- **Saves:** battery saves in `userdata/emulators/rgds-play/saves/<system>/`, checkpoints in `userdata/emulators/rgds-play/states/` and `library/<key>/auto-rgds-play.dss`, all in **Back up all saves**. The rules under Saves below apply. A checkpoint is mGBA's own state file: the machine, then an extra-data block with the cartridge RAM (no clock metadata, so the same moment always gives the same bytes). mGBA's bare machine state leaves that RAM out, and a game that keeps its working variables there (Super Mario Land 3) hung when the auto-load put the machine in before the first frame, beside the battery's RAM from another moment. Loading puts the RAM into memory only: the battery on the card follows when the game next writes it, so an older checkpoint never rolls an in-game save back by itself. Checkpoints made before 26 October 2026 are the machine alone and still load.

### Trying it on the handheld

```sh
python3 tools/build.py device && python3 tools/build_play.py device
python3 tools/play_device.py install     # a test release beside the installed one, then RG DS Core restarts
python3 tools/play_device.py rollback    # back to the release that was active before
```

`install` copies the active release to `releases/<build>-play<hash>`, replaces what `tools/package.py` would replace from this tree (launcher, bridge, runtime, assets, themes, `emulators/rgds-play`), writes the copy's manifest, verifies it and activates it with the release's own `activate.py`. The installed release is never modified, and `userdata` keeps every save and setting. A staged over-the-air update is not touched: it can only be installed while its own base release is active.

## How the companion finds the map

The idea comes from kyannon's [GBA DS](https://github.com/kyannon/gba-ds), which showed it works. RG DS Play is our own implementation of it.

1. **A shadow copy.** Next to the live game, the player keeps a second, silent copy of the same game: its own memory, no sound, no battery file.
2. **A snapshot, never a pause.** When it's time to look, the live game's state is copied (about 400 KB, well under a millisecond), and the shadow loads the copy. The game you're playing is never paused, slowed or written to. `tests/test_play.py` checks this frame by frame: an 800-frame run gives the same picture hash for every frame with the companion off, on in lockstep, and on racing the game as it does on the handheld.
3. **Open the map in the shadow.** The shadow lets go of every button for two frames (so a button the player is holding still reads as a fresh press), then plays the profile's `open` buttons.
4. **Trust, but check.** A capture is accepted only when the profile's memory condition says the map is up, its pixel probes match, and the picture has held still for `stable` frames. Then a few more frames are recorded so the player marker keeps blinking. A blank map is rejected. A failure keeps the last good map on screen.
5. **When to look:** every `interval` frames (1.5 s by default); 10 frames after a `room` value changes; 12 frames after a fade to black ends (a room transition); and only while `live` matches (in gameplay, not in a menu). Back on the title screen (`menu`), the old map is dropped.

On the bottom panel the map is drawn at the largest whole scale that fits, on the map's own background colour from edge to edge, so it reads as the game's second screen rather than a picture in a box. A change bigger than the marker moving cross-fades over 12 frames. The panel is redrawn only when what it shows changes.

**Cost on the RG DS:** with the test cartridge, a capture took about 80 ms of shadow emulation on a worker thread at `nice 10`. At one capture per 1.5 s that is about 5% of one A55 core; the live game's thread is untouched. Real games open their map more slowly, so measure each new profile.

## How the HUD moves

The live core gets a second mGBA software renderer (`play/src/core/mgba_split.c`). It is told about every register, palette, VRAM and sprite write the game makes, so it always has what the game's own renderer has, but it draws only the HUD layers (the profile's BG layers, and the sprites of one priority, through filtered copies of sprite memory), on a key colour where there is no HUD. While the profile's `on` condition holds, the game's renderer leaves those layers out. Only drawing changes: over 5,401 frames of Super Circuit (title, menus, a race, the split switching on), the emulator's whole state hashed the same every frame with the split and without it. `tests/test_play.py` checks this on the test cartridge always, and on Super Circuit when `RGDS_PLAY_ROMS` points at a folder with your dump.

The second screen is laid out by the profile: each `panel` box of the HUD gets a slot and is drawn at the largest whole-pixel scale that fits it. `trim` cuts a box down to what the HUD has drawn in it this race, so each course's map fills its slot whatever its shape. Behind the HUD is the game's own scenery, drawn by a silent copy with only the scenery layers (no karts, no Lakitu, no HUD) every ten seconds on its own thread. `to_game` boxes go back onto the game screen where the player looks (Super Circuit: the item box and your place). A profile without `panel` boxes shows the whole HUD as wide as the panel takes it (2.67x for a GBA screen on 640x480), grown to the next whole size and smoothed down like the game screen's sharp fit, its see-through parts blending into the second screen's ground.

On the Game Boy the HUD is usually a band of whole rows: the window layer at the bottom (Link's Awakening, Metroid II) or a status bar kept at the top (the Oracle games). A `[hud]` with `strip = 0 y w h` needs no second renderer: while `on` holds, those rows are cut from the game picture (the top panel shows a shorter picture, at a larger scale) and drawn at a whole scale along the bottom of the second screen, under the map, team or view. With a screen filter on, the player names its game texture to the bridge (`rgds_play_screen`), which then shades the shorter picture as a screen of its own size; only with a bridge that has no such call does the top panel keep the whole picture for the filter.

**Cost on the RG DS, Super Circuit racing (600 frames):** emulation 4.9 ms a frame alone, 5.3 ms with the split; drawing both panels in software 2.5 ms (the windowed player draws the top one on the GPU). About 8 ms of a 16.7 ms frame.

## Profiles

A profile is a text file in `play/profiles/<system>/`, picked by the game code in the ROM header. Profiles are data: adding a game, or fixing one, needs no rebuild. Game Boy and Game Boy Color profiles live in `profiles/gb/`; carts older than the Game Boy Color carry no game code, so their profiles name the header title instead, upper case with `_` between words (`POKEMON_BLUE`, `METROID2`).

```ini
[game]
title = Metroid Fusion
codes = AMTE                    # one or more 4-letter game codes

[companion]
live = mem8[03000BDE] == 01     # in gameplay: captures make sense
menu = mem8[02000000] == 0      # title/file screens: forget the map
room = mem16[02000002]          # values that change on entering a new room
interval = 90                   # frames between routine captures
dim_when_unavailable = no
note = The time and your gold appear once you're farming   # what the second screen will show

[map]
release = 2                     # frames with nothing held before `open`
open = START:4                  # buttons:frames, "-" for nothing, B+UP for both
timeout = 180                   # frames to wait for the map
stable = 3                      # frames in a row that barely change
max_diff = 640                  # pixels that may change between them (blinking)
ready = mem8[03000BDE] == 03    # memory says the map is up
pixels = 0,0=#9C9C9C 239,0=#9C9C9C
pixels_min = 0                  # how many probes must match (0: all)
tolerance = 8
background = #9C9C9C            # the map's empty colour (default: the most common edge colour)
min_foreground = 12             # pixels that must differ from it
crop = 0 0 240 160              # x y w h kept
anim_frames = 8                 # frames recorded for blinking markers
anim_step = 4
layers = 1F                     # BG0-3 and sprites drawn in the capture

[hud]
on = mem16[04000000] == 1F41    # the HUD moves to the second screen
keep = mem16[04000000] == 1F41  # the last HUD stays up (paused)
bg = 1                          # BG layers that are HUD (bit 0 = BG0)
sprites = 0                     # sprites of this priority are HUD (none: no sprites)
backdrop = game                 # behind the HUD: the game's scenery, theme (the second screen's own ground), or #RRGGBB
backdrop_layers = E             # drawn by a silent copy with only these layers
backdrop_rows = 76              # only the rows above the horizon
moves_when = mem16[06003808] == C044   # the layout below applies (racing, not results)
to_game = 104 0 33 29 > 4 4     # a HUD box put back on the game screen at X Y
panel = 140 64 100 96 > 136 84 488 380 trim   # HUD box > slot on a 640x480 panel
sprite_tiles = 256-295 0        # sprites by first tile (and priority): HUD too
window_effects_off = 1          # no shade inside WIN0 (1) / WIN1 (2) on the game screen
bg_priority_below = 2           # HUD = the BG layers below this priority (games that move menus between layers)
map_cnt = 4C03                  # on only while some BGxCNT holds this (the map's layer)

[party]
format = pokemon3               # pokemon1/2/3 (Red/Blue, Gold/Silver/Crystal, Ruby to LeafGreen), goldensun, saga1
count = 03004350                # the member count (pokemon3) or party flags (goldensun)
slots = 03004360                # the first member
icons = 083BBD3C                # ROM icon table, palette indices and palette table (pokemon3, optional;
icon_palette_index = 083BC41C   # checked against the palette table's tags, so another revision
icon_palettes = 083BC5D4        # shows no icons rather than noise)
names = 1:DE41                  # pokemon1/2: nicknames; dex_order and icon_kinds: their ROM tables

[view]
format = metroid2               # a second screen the player draws itself (companion/view.hpp):
on = mem8[FF9B] == 04 | 08      # metroid2, board or pokemon_battle; shown while `on` holds
level_bank = D058               # the format's own keys, mostly addresses

[map.dungeon]                   # another capture, used instead of [map] while `when` holds
when = mem8[DBA5] == 01 and mem8[FFF7] in 00..08
open = START:4                  # the same keys as [map]

[hud]                           # Game Boy: a band of whole rows instead of layers
on = mem8[DB95] == 0B and mem8[FF4A] == 80
strip = 0 128 160 16            # x y w h: full width, at the top or the bottom
```

Game Boy addresses can name a bank: `1:DCD7` is work RAM bank 1 (Game Boy Color games switch banks mid-frame, so the bus alone reads the wrong one half the time), `1C:590D` is ROM bank 1C. They work in conditions (`mem8[1:DCD7] == 01`) and in every address key.

The silent copy that captures maps starts with the live game's battery memory, and gets it again whenever the game saves: the European Oracle games keep their language there, and draw garbage without it.

With a `[party]` section and no map or HUD on show, the second screen draws the team live from memory: one card per member with its icon, name, level, an HP bar (and PP for Golden Sun) and status.

Two `[view]` formats serve any Game Boy game:

- **`board`**: a status board of numbers the game keeps in memory, drawn as launcher cards: `tile1 = Coins | bcd A97A 2 art coin`, in number order. Kinds are `bcd ADDRESS BYTES` (two digits a byte, the first byte the highest; `low` for a little-endian word of BCD), `num ADDRESS SIZE` (little-endian; `big`, `mask HEX`) and `bits ADDRESS BYTES` (how many are set, up to 32 bytes for a Pokédex). `count ADDRESS BYTES is HEX` counts the bytes that hold one value (one kind of item in an inventory of slots). `div N` divides (health in quarters), `times N` multiplies (a score kept in tens), `plus N` adds (lives kept one less than shown), `of N` adds a meter (`max ADDRESS` reads its most from a byte: health whose most grows) (for bits up to 16 with an icon: a row of them), and `wide` gives the tile a row of its own. Every tile has a badge: `icon NAME` (`play/src/ui/icons.hpp`) or `art NAME`, the game's own tiles from its ROM (`art.coin = gb 11:73F0 1x1`), drawn in the palette the top screen uses. `page NAME` puts tiles on pages, shown as tabs in the header and chosen by touch. `tiers` turns the value into named steps from `tiersN = 300 Birdhouse; 10072 Tree trunk` with a meter to the next, and `names` does the same for plain names (a sword's level, day or night). `heading` and `heading_art`/`heading_icon` title it, `proper = A; B` lists the game's own names (which stay untranslated), and `covers_hud = yes` shows it in place of a `[hud]` strip's band rather than above it (the band still leaves the game picture).
- **Boards over a Game Boy Advance HUD split:** `Label | hud X Y W H` is a tile of the HUD itself, what the split draws in that box of the game screen (a copy ability's name, a row of hearts, a coin counter), trimmed to what is drawn and as large as the tile takes it, and `art.NAME = hud X Y W H` makes a badge of it. `or X Y W H` names another place for the same piece (Advance Wars draws its panels on the side away from the cursor), and the first box with something drawn is shown; `tall` makes a tile's row twice as high, for a panel that would otherwise come out at 1x. With `covers_hud = yes` such a board takes the HUD picture's place on the second screen. It claims only its boxes: whatever else the HUD layer draws (dialogue, a boss's name and health, a message, the buttons) goes back onto the game screen, so nothing the game says is lost. The board waits until the HUD draws something in its boxes, so a cutscene that hides the HUD leaves the second screen quiet.
- **Several views:** `[view.<name>]` sections beside `[view]`, and the first whose `on` holds is shown (Wario Land: Super Mario Land 3 has a course board and a world-map board). A view with `alternative = yes` waits behind the **switch** (top right): a tap flips between the game's own screen (the map, the team) and that board, and with nothing else to show it shows by itself. Link's Awakening, the Oracles and Wario Land 3 have status boards there, and Pokémon Red, Blue, Yellow and Crystal have trainer cards.
- **The look and the rules** are in [COMPANION.md](COMPANION.md): the launcher's Theme (passed as `--preferences`), its language, touch, the dock, and the lint that checks every profile.
- **`pokemon_battle`**: the Game Boy Pokémon games' battle: the opponent (icon, name, level, types, HP) and yours with its four moves (type, power, PP left of its most, PP Ups counted), names from the cartridge's own tables. Keys: `generation` (1 or 2), the battle structs `player` and `enemy` and their nicknames `player_name` and `enemy_name`, the ROM tables `move_names`, `moves` and `type_names`, and the `[party]` icon keys. A view that shows comes before the team, so the battle replaces the team panel until it ends.

- **`course`**: a Mode 7 racing game's course from above, as Mario Kart DS has it (Super Mario Kart). The whole 1024x1024 course comes from video memory (its tile map in the even bytes, the tiles in the odd ones), drawn once at the panel's size (each pixel the mean of the course under it) and again only when the tile map changes (a new course, checked every half second) or the course's half of the palette does (at most once a second; the sprites' half flashes every frame). Each racer stands at the place the game keeps for it (`places = X Y STEP COUNT`, 16.8 with the fraction byte first), drawn as the kart the game's map shows for it: `sprites` is the map's sprite table in RAM, grouped as for `extend_sprites`, and `tiles` the first tile of each racer's kart. The first place is the player's, ringed in the accent and drawn last. Other map sprites (items) stand where the map has them. `ranks = ADDRESS DIV` (the same step) gives the standings beside the map, the racers' karts in place order with the player's row in the accent, clear of the dock's corner; `lap` (an expression) and `laps` put the lap over them. A tap goes on to the course close up (about 180 units across, sampled every other pixel), turning so that ahead is up (from where the race's last line looks on the course to where its first does), then to the game's own lower picture (the `[hud]` band: the view stops covering it), then back. Drawn at half the frame rate.
- **`mosaic`**: a map of everywhere the player has been, made from the game's own picture: every few frames the playfield (`crop`, in the `native` frame; a core that crops overscan shows its middle) is pasted, `scale` world pixels to a map pixel, where the expressions `x` and `y` say the frame's top left is in the world, one map per `area` value, the player (`player_x`, `player_y`) blinking on it. `when` holds off pastes mid-scroll, and a playfield of one colour (a fade) is never pasted. `lag = 1` pastes with `x` and `y` of the frame before, for games that scroll the screen in the vertical blank after moving their camera (Sonic, QuackShot: without it every paste lands a frame's scroll off and the map shows seams). The whole area fits the panel at the largest whole zoom (`zoom` sets the least, so a long level is shown larger around the player), or a big one follows the player. Kept beside the save (`RGMS`). For games with no map (Metroid) or one in a menu (Zelda's levels, Super Metroid). Checked on Metroid II through mGBA.
- **`grid`**: an automap for a first-person dungeon kept in memory as squares (Phantasy Star's 16x16 floors): `cells`, `position` (y high nibble, x low), `facing` (0 up, 1 right, 2 down, 3 left), `level`, `type_mask` and the hex kinds `open`, `wall`, `up`, `down`, `door`. A square is drawn once the player has seen it: the corridor ahead (`sight` squares, stopped by anything not open) and the squares beside each step, as the game draws them. Kept per level (`RGGR`).
- **`trace`**: a course map from where the player has driven (F-Zero keeps no map, only the machine's place): the first lap draws the road, later laps run on it. `x`, `y`, `course`, `when`, `wrap_x`/`wrap_y`, and `width` (the road's width in the game's units, hex; default 40). Each stretch driven is painted at that width into a grid of squares an eighth of it across, so a second lap on another line widens the road a little instead of drawing a second squiggle. The squares are blurred and read back between them, so the edge is smooth at any scale, with a kerb in the accent and a soft shadow. A long course whose road would come out thinner than a finger is painted wider on screen. The player is a blinking disc with a nose toward where it is going. A game with a table of its racers (`racers`, `racer_exists`, `racer_x`, `racer_y`, `racer_rank`, `racer_lap`, `racer_kind`, `laps`) puts them all on the map with the lap and standings beside it, as faces if `faces` and `face.N` say where its ROM keeps them; the format is at the top of `trace.cpp`. The picture is redrawn at most twice a second while the road grows. A game that keeps its course's path for its computer drivers gives the whole road at once: `path` (the first point's address, an expression: `mem32[164550] & 7FFFFF`), `path_count`, and optionally `path_left`/`path_right` (the edges, point for point, for the road's width), `path_stride` (decimal, 8), `path_x`/`path_y` (hex offsets of the signed 16-bit coordinates). The start line is drawn where the path begins, and driving then paints nothing (a shortcut over the grass is not the road). Kept per course (`RGTR` 3: the squares; version 2's points are painted as strokes when read).
- **The keyboard** (`companion/keyboard.cpp`, no profile needed): a ZX Spectrum, Commodore 64, MSX, Amstrad CPC, Amiga, DOS or Flash game has its computer's keys on the second screen, on the switch beside the game's own views and on its own while it has none (so on Out Run's menus, and the whole time in a game without a profile). It is the last view in the list and counts as the alternative, so a profile for these systems keeps its own boards as plain views: only the first alternative shows. One finger at a time, so the shift keys stay down until the next key has been pressed, and on the Spectrum the keys then show their symbols. The C64 has two pages (`More`). A tap holds its key at least four frames. Cores get them through `Core::set_key` in libretro's key codes: Fuse reads them (`RETRO_DEVICE_KEYBOARD`, on its third port), VICE hears them (`SET_KEYBOARD_CALLBACK`) and takes them through its positional map, which is why the C64's `+` is `RETROK_MINUS`. The MSX has two pages too (`F1-F5`), and blueMSX polls the keys (`RETRO_DEVICE_KEYBOARD`) through its own map: GRAPH is `RETROK_LALT`, STOP `RETROK_END`, SELECT `RETROK_PAGEUP`. Its cartridges run on the free C-BIOS machines the image carries (`/usr/share/libretro/bluemsx`, copied into the BIOS folder before a game starts without replacing the owner's files); disks and tapes need the owner's own MSX machines there, as RetroArch's blueMSX pack lays them out. The Amiga's keys go to PUAE through its keyboard callback (positional, US: HELP is `RETROK_INSERT`, the Amiga keys Page Up and Page Down); its right stick is the mouse (`puae_analogmouse=right`, buttons on L2/R2) and the left stick its joystick, so the Amiga keeps its sticks as sticks (`stick_buttons.hpp`). PUAE starts on AROS, its free Kickstart replacement, unless a Kickstart of the owner's is in the BIOS folder (a name starting `kick` or `amiga-os-`, or with `kickstart` in it); WHDLoad sets and many games need the real one.
- **The touch controllers** (`companion/keypad.cpp`, no profile needed): a ColecoVision or Intellivision game has its controller's twelve-key keypad on the second screen (`*` and `#`, or Clear and Enter, beside 0), and a Sega Pico game its storyware book and drawing pad under the pen, and an Atari 2600 game the console's switches (Game Select and Game Reset held while touched; the difficulty and TV type switches thrown, through `Core::set_panel_buttons`, which Stella reads as L/L2, R/R2 and L3/R3). An Atari 7800 game has its console's Pause, Select and Reset and its two difficulty switches, and an Atari 5200 game its controller's twelve-key keypad (see Atari 7800, 5200 and Lynx below). Like the keyboard, each is the last view and the alternative, and the Second screen picker offers it first (Keypad, Storyware). A keypad key is held while the finger is on it (at least four frames), and sliding to another key moves the press. Cores get them through `Core::set_keypad` (a 12-bit mask, keys read across the pad) and `Core::set_pico_pen`/`set_pico_page`, from hooks our packages add: `retro_rgds_keypad` (libretro-gearcoleco and libretro-freeintv 0001) and `retro_rgds_pico_pen`/`_page`/`_set_page` (libretro-picodrive 0001). The pen goes down where the finger is, in the 320 x 224 of the page or the pad, and lifts with it; A is its red button and L/R turn pages, as PicoDrive maps them. A page shows the owner's scan when one is beside the game under PicoDrive's own names (`Game_0.png` to `Game_6.png`, `Game_pad.png`), else a blank page that still takes the pen.
- **`events`**: a competition of events (California Games): each event (`names`) with the score that won it and who won it, the record to beat from the game's own table (`best`, `best_name`, `best_score`), the one being played standing out (`event`, an expression; past the last, the final standings), and beside them the players (`players`, `records`, `record_name`) ranked by their medals (`record_medals`: gold, silver and bronze counts, 5, 3 and 1 points). Each event's scores (`record_score`, text) are in the table only from when the event ends until the next begins, so the winners are kept beside the save (`RGEV`); other players, fewer medals or an earlier event start a new competition.
- **`route`**: a race through stages that fork (Out Run): a row of stages for each of `levels`, every stage leading to the two below it, numbered 1 at the top and then left to right a level at a time (`stage`, an expression). The way driven is drawn in the accent with each stage's time, the stage now with its running clock, the two roads ahead stand out, and a card under them has this stage's clock and the total. Times are the game's own text (`clock`, `last` and `total` = ADDRESS LENGTH, ASCII with the top bit dropped, like 2'18"3): `last` is read for the stage just done once the next has started, and the total is `total` (the stages done) plus `clock`. The way is kept beside the save (`RGRT`), and a stage 1 is the start of a new one.
- **Expressions** (`play/src/companion/expr.hpp`): the numbers these views read are hex numbers, `mem8/mem16/mem32[ADDRESS]` and `f32[ADDRESS]` (a 32-bit float's whole part: an N64's places) with `+ - * / << >> & |` and parentheses, C's precedence: `x = (mem8[EB] & F) * 100`.
- **`strip_fill = yes`** in `[hud]`: the band is a second picture of its own (Super Mario Kart's course map under the race) and fills the second screen's width instead of sitting in a card: grown to the next whole size, then smoothed down to the fit, as the game screen's sharp fit does. **`game_rows = N`** keeps only N rows on the game screen while the band is off, so a gap between the two pictures (Super Mario Kart's black rows 100-107) is on neither screen. **`extend = N`** draws N more Mode 7 rows under the game's own race view: the race is the run of scanlines from the first Mode 7 line that share one centre and scroll, its matrix follows a / (line - l0) (a plain perspective: a fitted constant bent the near rows), and the rows after it continue that curve over the course in video memory with the core's own arithmetic and palette, so Super Mario Kart's road goes on down the top screen (191 rows instead of 99). **`extend_sprites = ADDRESS`** puts what stands there on that road: the lower picture's sprite table as the game builds it in RAM (544 bytes in OAM's layout; Super Mario Kart writes its map's into OAM between the two pictures, so the core's own table holds only the race's). Its pieces are grouped as the game lists them (one after another, one palette, touching), each group's centre on the map is a place on the course, and it stands where the extension's rows look at that place, a quarter of its height under it, larger the nearer the row, from its own tiles (OBJSEL read from snes9x's PPU, trusted only while its decoded sprite table agrees with its raw one). A map pixel is several course units, too coarse up close, so **`extend_places = X Y STEP COUNT`** names where the game keeps places exactly (16.8 fixed point, the fraction byte first; Super Mario Kart's racers at 7E1017/7E101B, every 100 bytes) and **`extend_tiles`** the first tile of each place's sprite (each racer's kart is drawn from tiles of its own): a group drawn from those tiles stands at that place, and the first place, the player's, is left to the race view. It needs a core that exports its per-line Mode 7 record and PPU (`LineMatrixData`, `PPU`): our snes9x (`os/buildroot/package/libretro-snes9x/0001-export-mode7-line-data.patch`) and the libretro buildbot's macOS build do; with any other the game keeps its 99 rows. `play-shot` takes `--core`/`--system` like the player, and `state save|load FILE` in `--drive`. The board's `clock` word shows a two-byte num (minutes, then hours) as 18:05.
- **Light guns:** `lightgun = yes` in `[game]` makes the second port the core's light gun (the NES Zapper in FCEUmm): the game starts on the touch screen (swapped) and a finger aims and fires there, the trigger held four frames so the game sees the shot.
- **Mice:** `mouse = yes` in `[game]` makes the first port the SNES Mouse (snes9x), the game on the touch screen as for a light gun. `cursor_x`/`cursor_y` (expressions) say where the game keeps its pointer: each frame the mouse moves half the way from there to the finger, and the left button holds only once the pointer is there, so a stroke starts where the finger lands and no line is drawn from where the pointer was. A is the left button, B the right, the D-pad nudges the pointer; without `cursor_x` the mouse counts its own moves. snes9x keeps the mouse's place as the sum of every move outside its state, so a mouse game's states carry that sum after the core's bytes (`RGMO`) and a load in a new run puts it back (else the pointer stands still for seconds while the core walks the gap). Mario Paint (`snes/MARIO_PAINT`, pointer at 7E04DC/7E04DE) was checked on the Mac through snes9x: the title's gags, a stroke on the canvas from (40, 60) to (200, 150) where the finger went, and a state loaded in a new run.

A `[map.<name>]` section is a second screen captured instead of `[map]` while its `when` holds; the first that holds wins. Link's Awakening captures the island map with SELECT outdoors and the dungeon's floor map from the inventory (START) inside one.

Conditions are `memN[address] [& mask] == a | b`, `!= a`, or `in lo..hi`, joined with `and`; addresses and values are hex. A parse error names the file and line, and that profile is skipped; the game still plays.

### NES, SNES, Mega Drive, Master System and N64

The libretro systems find their profiles in `play/profiles/nes`, `snes`, `md`, `sms`, `n64`, `zx`, `c64`, `gw` and `scummvm` (the runtime passes all eleven folders; the launcher knows an N64 game by its file's name only, as summing a 12 MiB cartridge is too slow while the library scans). A game is known by its cartridge's CRC-32 without a dumper's header (`CRC_3FE272FB`), by a SNES cartridge's own name (`SUPER_METROID`) or a Mega Drive cartridge's overseas name (48 bytes at 150: `SONIC_THE_HEDGEHOG`), or by its file's name made a code (`Legend of Zelda, The (USA)` → `LEGEND_OF_ZELDA`); the launcher's two-screens mark finds them the same way (`src/launcher/dual_screen.hpp`). `peek` reads the system's own addresses: the core's memory map where it gives one, else an NES's 0000-07FF and cartridge RAM at 6000, a SNES's work RAM at 7E0000-7FFFFF, a Mega Drive's 68000 work RAM at FF0000-FFFFFF (PicoDrive keeps it as 16-bit words in the host's order, so a byte is at its address ^ 1; numbers are read big-endian), a Master System's at C000-DFFF, an N64's RDRAM by physical address, written without the CPU's 80 (`0F69A4` for 800F69A4: a profile address's top bit marks a banked one; mupen64plus keeps it as 32-bit words in the host's order, so a byte is at its address ^ 3; numbers are read big-endian). FCEUmm runs with eight rows of overscan off the top and bottom (256x224) so profiles can name rows. The ZX Spectrum plays through Fuse (`fuse_libretro.so`) as a Spectrum 48K (a 128K only for a tape named for the 128K alone, or whose TZX header says it needs one: `play/src/core/zx_machine.hpp`; Fuse's own choice gave a 128K to anything with 128 in its name, such as Out Run's `[48-128K]`, whose loader then reset the machine to BASIC) with no border (256x192), the pad as a Kempston joystick (Start is Enter, L2 Space, nothing else: digit keys on X, Y, L and R were read by games as the Sinclair/Cursor joysticks, so R sent Out Run's accelerate; menu numbers come from the second screen's keyboard, Select Fuse's keyboard overlay). Fuse's fast load breaks SpeedLock's loaders (Out Run never got past its loading screen), so tapes play at the machine's own speed and the player runs 16 more of the machine's frames per frame shown while a loader reads the tape, silently: our Fuse's `loader_tape_loading` (`os/buildroot/package/libretro-fuse/0002-loader-tape-loading.patch`) is true while ten or more loader-like reads of port FE came in the last two frames, as Fuse's own loader detection judges them (a loader reads 550-1200 times a frame, Out Run's race 0-1), and the same patch stops a tape no loader has read for three seconds, so a multiload game that races with the tape still playing finds its next part where the last one ended; with another Fuse the player hurries while the tape plays with interrupts off. Out Run reaches its menu in about 15 seconds. A tape game sitting at BASIC's prompt (a load that failed or was stopped) is never kept as the resume state, and a kept state that holds only that prompt is refused, the tape loading from its start instead (`zx_at_prompt`: the ROM editor's error handler, 107F, is on the stack where ERR_SP points); `peek` reads the Z80's 64 KiB as paged now, through Fuse's `memory_map_read` (exported by `os/buildroot/package/libretro-fuse/0001-export-memory-map.patch`; the buildbot's macOS build exports everything). The Commodore 64 plays through VICE's fast x64 (`vice_x64_libretro.so`, autostart, warp while loading, the pad on joystick port 2); `peek` reads its 64 KiB of RAM. Their games are known by the file's CRC-32 and name (`Out Run (1988)(U.S. Gold)` → `OUT_RUN`). A `.tap` is a Spectrum tape unless it is in a `c64` folder, and an `.m3u` in a `c64` folder lists a C64 game's disks (the launcher hides the disks an `.m3u` lists). The keyboard has a Disk button for a game on several disks (an `.m3u`; through `RETRO_ENVIRONMENT_SET_DISK_CONTROL_INTERFACE`, `Core::set_disk`): a tap puts the next disk in, as the game asks for its other side. QuackShot's Rev A cartridge (the common 512 KiB dump) wires its lower half to 000000-0FFFFF and its upper half to 100000-13FFFF, and jumps there at boot; Genesis Plus GX maps it so, PicoDrive does not and hangs on a black screen, so the player hands PicoDrive a copy laid out as the bus sees it (a temporary file, removed when the game closes).

### Game & Watch

The Game & Watch and the other LCD games run through [gw-libretro](https://github.com/libretro/gw-libretro), with MADrigal's simulators in `/data/roms/gw` (`.mgw`, the owner's own; they do not ship with RG DS OS). A simulator's picture is a scan of the whole machine, and `[screens]` in a profile says what part of it each panel shows:

```ini
[screens]
top = 0 -82 606 454             # x y w h of the picture; past its edges is black
bottom = 0 372 606 454          # optionally "from to" after them: the columns it keeps
same = A+B                      # a machine with one action button: either of the pad's
touch = 496 416 48 40 L         # that part of the picture is that button, under a finger
```

- **Multi Screen** machines split at the hinge. Those that open like a book (Mario Bros., Lifeboat, Penguin Land) put the left half above the right.
- **Panorama, Table Top** and the tall ones show the LCD above and the controls below; **Wide Screen** and other flat ones the LCD large above and the whole machine below.
- **Start and Select** are Game A and Game B (or a power switch), L and R too, L2 Time and R2 ACL. The core's own menu and help never appear. Pressing a button gives a short click in the motor.
- **No checkpoints:** the core can't save its state (the game runs in Lua), so `NO_CHECKPOINTS` in `runtime/play_options.py` makes Home and the switcher leave without one. Battery files keep what the simulators remember.
- **Covers** come from the scan inside the simulator, closed if it has one (`runtime/gw_art.py`), through Find artwork.

`play/profiles/gw/` is written by `tools/gw_layouts.py`, which measures each machine with the core: every LCD segment is lit until a game starts, and a button is drawn pressed while its key is held. Six dark LCDs are hand-read (`LCD_BY_HAND`). Profiles match a simulator file by its CRC, so another build of one gets no layout: the whole machine on the top screen. `package/libretro-gw/0001` keeps the game keys beside the core's menu for simulators in the older format.

### Arcade

Arcade sets are the owner's own `.zip` (or `.7z`, which FBNeo also reads) files in `/data/roms/arcade` (or an `arcade`, `mame`, `mame2003`, `mame2003-plus`, `fbneo`, `fba`, `finalburn`, `neogeo`, `cps1`, `cps2` or `cps3` folder). Two cores play them: [FinalBurn Neo](https://github.com/libretro/FBNeo) (`package/libretro-fbneo`, about 55 MB) every set but Nintendo's two-monitor cabinets, which are mame2003-plus's (below). `runtime/play_options.py` `libretro_core` picks by the set's name.

- **The set list:** `assets/arcade/sets.tsv`, written by `tools/arcade_sets.py` from FBNeo's arcade DAT at the package's pinned commit (8,760 sets, 2,615 of them vertical), with a clone's parent and flags: `b` a board's BIOS, `v` a vertical monitor, `x` FBNeo marks it not working, `m` a two-monitor cabinet. Bump the package and run the tool together. The library lists the sets in it under their titles (`arcade_catalog()` in `src/launcher/model.hpp`); a board's BIOS (`neogeo.zip`, `pgm.zip`) stays unlisted beside the games that need it, and a zip no core here knows is left out. Sets must match FBNeo's names and CRCs (FBNeo refuses a set with a wrong ROM and shows what is missing); a clone in split sets needs its parent's zip beside it. Bring over takes an old card's sets in those folders that the list knows, BIOS included.
- **The tall screen:** a vertical game (Galaga, 1942, the shoot-'em-ups) stands over both panels as one screen twice as tall, 640×960: its upper half on the upper panel, standing on the hinge, its lower half on the lower one, hanging from it, at one scale (a 224×288 game at 2.86×). FBNeo draws a vertical game on its side and asks the frontend to turn it (`RETRO_ENVIRONMENT_SET_ROTATION`): the player turns the frame upright as it converts it (`rotated` in `play/src/core/libretro_core.cpp`), so every view, checkpoint picture and rewind thumbnail sees the game standing. A vertical set no profile names gets the layout from `tall_profile()` (`play/src/companion/profile.cpp`): `[screens]` with `tall = yes` and the board's own pad, which a profile can also say. The rectangles follow the picture's size, each half in a box of the panels' 4:3 shape; while the picture is wider than tall (a board's sideways test screen) it is shown whole above. The upper half fills its panel with no frame (a frame or whole pixels would size the halves apart); Swap is not offered, as it would stand the halves upside down; Second screen off, the info screen and Turn off screen (anything that covers the lower panel) show the whole game on the upper panel. The launcher gives vertical sets the two-screens mark (`dual_screen.hpp`).
- **Options:** FBNeo's vertical mode off (the player turns), 32-bit colour, high scores on (they need FBNeo's `hiscore.dat` in the BIOS folder's `fbneo`). Holding Start opens FBNeo's diagnostic menu (dip switches, service mode). Select is the coin, Start the start; buttons are FBNeo's RetroPad layout for the board.
- **Checked on the Mac only:** FBNeo built from the pinned commit; Galaga (rotated three quarter turns, its board's flipped monitor), 1942 and Street Fighter II from zero-filled sets carrying the right CRCs, through a test build of FBNeo that ignores the CRC of the bytes (the shipped one checks them): 224×288, 224×256 and 384×224 frames, the two vertical ones over both panels; a test core drawing four colours showed the turn is a quarter counter-clockwise, as libretro means. `test_tall_screen` (`play/tests/play_tests.cpp`) checks the layout pixel by pixel. Not built in Buildroot, not on the handheld, no real set played.

### Arcade: two-monitor cabinets

Nintendo built a few arcade cabinets with two monitors, and each maps one to one onto a panel. They run through [mame2003-plus](https://github.com/libretro/mame2003-plus-libretro), built with only these boards: `os/buildroot/package/libretro-mame2003-plus/two_monitors.py` cuts the driver list, the driver sources and the CPU and sound cores down (Z80, 2A03; NES APU, VLM5030, DAC) as a post-patch hook, so the core is a few megabytes instead of forty. These sets are named as MAME 0.78 names them (flag `m` in the set list), and go to this core whatever FBNeo calls its own Punch-Out!!.

| Sets | Cabinet | Frame | Profile |
| --- | --- | --- | --- |
| `punchout`, `spnchout`, `spnchotj`, `armwrest` | Punch-Out!!, Super Punch-Out!!, Arm Wrestling: one monitor stacked on the other | 256×448, upper monitor first | `arcade/PUNCH_OUT.ini`: rows 0-223 up, 224-447 down |
| `vstennis`, `wrecking`, `balonfgt`, `vsmahjng`, `vsbball`, `vsbballj`, `vsbbalja`, `iceclmrj` | Vs. dual system: two NES boards, a monitor for each side | 512×240, first player left | `arcade/VS_DUAL.ini`: left half up, right half down |

- Profiles match by the set's name (`PUNCHOUT`). `match` keeps the split to the frame's size; `pad = plain` passes the pad through untouched, unlike a Game & Watch's: **Select is the coin**, Start the start.
- Buttons are mame2003-plus's RetroPad layout: B, A and Y are the cabinet's first, second and third buttons (Punch-Out!!'s two punches and its KO punch; a Vs. board's NES B and A).
- On a Vs. dual board the pad is the left side's first player, whose monitor is the upper screen. That side's second start button (MAME's P3 Start, for two players on one side) is not on the pad: one pad, one player.
- A clone (`spnchotj`, `vsbballj`, `vsbbalja`) in split sets needs its parent's zip beside it, as in any MAME folder.
- `ARCADE_SETS` (`runtime/play_options.py`) names these sets for the core choice; a test keeps that list, the core's, the set list's `m` rows and the profiles' codes the same.
- The core goes straight into the game (`mame2003-plus_skip_disclaimer`, `_skip_warnings`); its states work, so checkpoints, rewind and the Save/Load gallery are as for any system.
- Second screen off puts the whole frame on the upper panel, both monitors small.
- **Not run with real sets yet:** on the Mac, zero-filled sets with MAME's file names start, give 256×448 and 512×240 frames that land on the two panels, and save and load states (`test_two_monitors` in `play/tests/play_tests.cpp` checks the split pixel by pixel). Built in Buildroot (4.2 MB stripped, libc and libm only) and in the slot-only image `os38f77023`; never on the handheld.

### Virtual Boy

Virtual Boy games run through [Beetle VB](https://github.com/libretro/beetle-vb-libretro) (Mednafen), `.vb` and `.vboy`, or `.bin` in a `vb` / `Virtual Boy` folder (`/data/roms/vb` on RG DS OS). No BIOS.

- **Both eyes, always:** the core runs in its side-by-side 3D mode with no gap (`vb_3dmode`, `vb_sidebyside_separation` in `play/src/core/libretro_core.cpp`), in the machine's own red on black. Its 768×224 frame is split in the player: `Core::picture()` is the left eye (384×224) and `Core::other_eye()` the right one, so every view, checkpoint picture and shader sees one ordinary 384×224 game.
- **Second screen → 3D: one eye each** (the picker's fifth place, stored as `second=keyboard` like the Dreamcast's VMU screen) draws the right eye on the lower panel with the same fit and bezel as the left eye above, so the two pictures match pixel for pixel. Changing it is live: no restart, as the core already draws both eyes. Companion, Info screen, Off and Swap behave as for any game, with the left eye as the game.
- **Controls:** the left D-pad is the D-pad (and the left stick), A and B, L and R, Start and Select as labelled; the controller's right D-pad is the right stick (`vb_right_analog_to_digital`). L2 and R2 are kept off the core, which would read them as the right D-pad.
- **Bezel:** the visor in black with its red stripe and VIRTUAL BOY on the rail, on both panels in 3D.

### Atari 7800, 5200 and Lynx

Three more Atari systems, each on its own shelf with its own folder in `/data/roms` (`atari7800`, `atari5200`, `lynx`; also `Atari 7800`, `7800`, `Atari 5200`, `5200`, `Atari Lynx`, `atarilynx`). A plain `.bin` is the 7800's or the 5200's only in its folder.

- **Atari 7800** through [ProSystem](https://github.com/libretro/prosystem-libretro) (`package/libretro-prosystem`), `.a78`. The BIOS is optional (`7800 BIOS (U).rom` in the BIOS folder shows the Atari logo first). Buttons: B and Y are button 1, A and X button 2, Start is Pause, Select is Select. Reset and the difficulty switches are only on the second screen (**Second screen → Console switches**): the core reads Reset from X and the switches from L and R held, so a thumb on X or a shoulder never resets the game or changes its difficulty. The switches start at A, as the core reads them with nothing held, so the game sees the same whether the panel is up or not. Bezels: the 7800's black front with its silver strip, or the grey TV.
- **Atari 5200** through [a5200](https://github.com/libretro/a5200) (`package/libretro-a5200`), `.a52`. The owner's `5200.rom` when it is in the BIOS folder, else the free Altirra 5200 OS the core carries (a few games need the real one). The left stick is the 5200's analog stick (kept a stick, as the N64's is: `stick_buttons.hpp`), the D-pad the same digitally; A is Fire 1, B Fire 2, Start and Select are Start and Pause. The keypad is the second screen's (**Second screen → Keypad**), through `retro_rgds_keypad` (our patch 0001, one key at a time as the controller reads them); L, L2 and R2 are kept off the core, which would open its own on-screen keypad over the game or press 9, 3 and 1. Bezels: the 5200's long black front, or the wood-grain TV.
- **Atari Lynx** through [Handy](https://github.com/libretro/libretro-handy) (`package/libretro-handy`), `.lnx`. `lynxboot.img` in the BIOS folder is used when there, else Handy starts the cartridge itself. Games made to be held upright (Gauntlet, Klax) are turned by the core from their cartridge header, so the picture is 102 x 160. Buttons: A and B as labelled, L and R are Option 1 and 2, Start is Pause. Bezel: the Lynx whole on the panel, wide and black, the pad on the left and A and B on the right; an upright game is fitted by its height (2.5x) inside it. RetroAchievements identify Lynx and 7800 games; the 5200 has no hash in rcheevos.

Tested on a Mac with each core built from the pinned source (`make`) and hand-made carts: a 7800 cart copying the console switches into RAM (the panel's B cleared bit 6, Pause held bit 3, the pad's X reached nothing), a 5200 cart painting the background from the keypad register (1 and # each changed it), and blank Lynx carts flat and upright (160 x 102 and 102 x 160). No real game, nothing on the handheld.

### WonderSwan and Neo Geo Pocket

Two shelves, each holding the first machine and its Color: `/data/roms/wonderswan` (also `ws`, `wsc`, `wswan`, `WonderSwan Color`) and `/data/roms/ngp` (also `ngpc`, `Neo Geo Pocket`, `Neo Geo Pocket Color`). Neither needs a BIOS. Covers, Game info and ScreenScraper look a Color game (`.wsc`, `.ngc`) up in the Color's own lists (`public_artwork.COLOUR_LISTS`); RetroAchievements has one console for each pair.

- **WonderSwan** through [Beetle WonderSwan](https://github.com/libretro/beetle-wswan-libretro) (`package/libretro-beetle-wswan`), `.ws`, `.wsc` and `.pc2`. A game made to be held upright says so in its cartridge's footer (bit 0 of the fourth byte from the end): the player sets the core to portrait for it, the core turns the picture (144 x 224) and the pad with it, so the D-pad is then the Y pad those games move with, the face buttons the X pad, and A and B are on L and R. Held sideways the D-pad is the X pad, A and B as labelled, and L, R2, L2 and R the Y pad's left, up, down and right. Start is Start; Select turns nothing. Frames go out at 60 Hz (the core drops every fifth of the machine's 75). Mono games in the WonderSwan's own LCD tint. Bezel: the WonderSwan Color, white or blue, whole on the panel at 2x; an upright game fitted by its height (1.75x).
- **Neo Geo Pocket** through [Beetle NeoPop](https://github.com/libretro/beetle-ngp-libretro) (`package/libretro-beetle-ngp`), `.ngp`, `.ngc`, `.ngpc` and `.npc`. The console's language is English. B is the Pocket's A (the lower, left button), A its B, Start is Option. A game's save is the cartridge's flash, which the core keeps in its own file (`saves/ngp/<game>.flash`, in the save backup with the rest of `rgds-play/saves`); upstream wrote it only when the game closed, so our patch 0001 writes it half a second after the game's last flash write, beside the old one and renamed over it, and a power cut or a crash keeps it. Bezel: the Neo Geo Pocket Color, silver or black, the game at 2.75x.

Tested on a Mac with both cores built from the pinned source (`make platform=osx`) and hand-made carts through `play-shot`: WonderSwan carts flat (224 x 144, 448 x 288 on the panel) and with the upright flag (288 x 448), a Neo Geo Pocket Color cart booting on the core's own start-up (160 x 152, 3x without a bezel), a checkpoint saved and loaded on each, and a Neo Geo Pocket cart writing its flash the way games do (the command at 0x205555, then a byte): the `.flash` file was on disk 30 frames later with the game still running. The four bezels drawn around these picture sizes with the frame code alone. WonderSwan games that change orientation part-way have no way to turn (Select is not the core's turn toggle here). No real game, no Buildroot build in Lima, nothing on the handheld.

### ScummVM

Adventure games run through ScummVM's libretro core (`package/libretro-scummvm`, the lite engines). A game is a folder in `/data/roms/scummvm`, named as the game: the launcher lists the folder (`scan_system`), passes the core a file in it (a `.scummvm` hook if there is one) and the core detects the game.

- **On the touch screen** by default: tap to click, hold for the right button, the top screen shows the title and box art.
- **SCUMM games with verbs** (`play/profiles/scummvm/SCUMM_VERBS.ini`, known by a file in the folder such as `MONKEY.000`): the scene on the top screen and the verbs and inventory large below. A finger is the mouse on both, using the top panel's own touch screen (`RGDS_TOP_TOUCH_DEV`, else the Goodix on `fe5c0000`).
- **Buttons:** A and B click left and right, the D-pad moves the cursor, X the game's menu (F5), Y skips a scene, L a line of speech, R pauses, Select the on-screen keyboard. **Start is ScummVM's menu**, for saving, loading and quitting; our `0001` patch tells the player it is up, so both panels then show it whole.
- **No checkpoints, but a game goes on from where it was left:** the core has no save states, and ScummVM by itself autosaves only every five minutes. Our `0002` patch writes the autosave as the game is left (Home, the menu's quit, ScummVM's Quit) and loads it at the next start. Nothing is written where the game itself refuses a save (a cutscene; the Monkey Island and Fate of Atlantis demos never allow one) or over a save of the player's own in the autosave slot. Seen with Beneath a Steel Sky and Sam & Max's demo (SCUMM writes its saves from its own loop, so the patch writes that one as the loop ends); other engines at least keep the five-minute autosave and start from it. Each game's saves live in a folder of its own, `userdata/emulators/rgds-play/saves/scummvm/<the game's folder>` (ScummVM names saves by the kind of game, so a demo and the whole game would share them).

To try one on a Mac the core needs `USE_MAD=0 DEBUG_ALLOW_DIRTY_SUBMODULES=1`, and hand fixes to its old zlib, libpng and FreeType for the current SDK.

### DOS

DOS games run through [DOSBox Pure](https://codeberg.org/schelling/dosbox-pure) (`package/libretro-dosbox-pure`, 1.0-preview7 from libretro's mirror). No BIOS.

- **A game is a zip of its folder** in a `dos` folder (`/data/roms/dos`; also `MS-DOS`, `msdos`, `pc`, `dosbox`). Pure opens the zip itself, so the player hands it over unpacked (`open()` skips `unpack_game` for `dos`), and a zip there is DOS even when it holds a `.cue` or `.iso` (`FOLDER_EXTENSIONS` lists `.zip` first). A `.dosz` is DOS anywhere; CD and floppy images (`.iso`, `.cue`, `.chd`, `.ins`, `.img`, `.ima`, `.vhd`, `.m3u`) only in the folder. A `.zip` outside it is still a DS game.
- **Start:** Pure runs the game's one program itself, and asks once (its start menu, on the top screen: D-pad and A) when a zip has several; it remembers the choice in the game's save.
- **The game's own saves** (and its SETUP choices) are what it wrote to its drive: Pure keeps them as `<game>.pure.zip` in `userdata/emulators/rgds-play/saves/dos`. Checkpoints are Pure's save states (`dosbox_pure_savestate=on`, no rewind): about 150 KB for a text-mode program, more with more memory in use.
- **The second screen is the keyboard first** (Second screen → Keyboard), a PC's keys over two pages (`F1-F12`: function keys, symbols, arrows, Home/End/PgUp/PgDn, Ins/Del, the keypad's `+` and `-`), then **Mouse**: a touch pad as on a laptop, the whole screen but a slim row of buttons left of the dock (no heading; a mouse drawn in the pad until it is first touched). Slide to move (a quick slide goes further), tap to click, tap then slide to hold the left button (dragging); the Left and Right keys under it hold their button while the finger is down, beside Esc, Enter and the way back. The pad goes to the core as relative motion (`Core::move_pad_mouse`, `RETRO_DEVICE_MOUSE` on port 0, `dosbox_pure_mouse_input=virtual`), so it moves the game's own cursor at its own speed.
- **Buttons:** Pure's own mapping for the games its keyb2joypad list knows (`dosbox_pure_auto_mapping`), else its generic keyboard one (the D-pad the arrows, the face buttons Enter, Space, Esc...). The sticks stay sticks (`stick_buttons.hpp`). Pure's L3 menu and on-screen keyboard are off: the second screen has the keys and the disk swap (the keyboard's Disk button, through the disk interface).
- **Frames:** the PC monitor; `aspect_correction` is left off (the player draws the picture at its own pixel size).

Tested on a Mac with the core built from the pinned source (`make`): a hand-made `.COM` reading the mouse (INT 33h) and keys (INT 16h) in a zip, driven by `play-shot --drive` taps: typed keys with sticky Shift, pad motion, tap click, right button, tap-and-drag, a state saved and loaded. Not yet on the handheld, and no real DOS game tried.

### Flash

Flash games run through [Ruffle](https://ruffle.rs) 0.8.0 (MIT/Apache-2.0), wrapped as a libretro core in `play/ruffle` (Rust; `package/libretro-ruffle`, `/usr/lib/libretro/ruffle_libretro.so`). No BIOS, no network: every file a game asks for is answered from its own files.

- **A game is a movie or a pack.** A `.swf` is Flash anywhere. In a `flash` folder (`/data/roms/flash`; also `Flashpoint`, `adobe flash`, `swf`) a `.zip` is a pack of the game's web files: Flashpoint's layout (`content/<host>/<path>`, a curation's `meta.yaml` with its `Launch Command`), or any zip of a game's folder (served from `http://localhost/`). Ruffle opens the zip itself (`open()` skips `unpack_game` for `flash`).
- **Where a game starts:** `<game>.flashpoint` beside it (lines of `key=value`) names the address (`launch=`), the FlashVars (`flashvars=`) and, for a Flashpoint legacy game, its `htdocs` folder; else a curation's `meta.yaml`; else the largest movie in the pack. A launch page (`.html`) is followed to the movie it embeds, with its FlashVars. The movie is loaded from that web address, so it sees its own site (site locks pass) and relative loads come from the pack; a name in another letter case, or the same file under another host when only one has that name, is found too. Pages the game opens are ignored and sockets never connect.
- **Flashpoint:** `runtime/flashpoint.py` imports the Flash games of a [Flashpoint Archive](https://flashpointarchive.org) install. On a computer: `python3 runtime/flashpoint.py import <Flashpoint folder> <card>/roms/flash` (copies; `--search`, `--limit`, `--extreme`). On the handheld: a Flashpoint folder copied into `roms/flash` is imported at the next start (the session runs `flashpoint.py scan`, which moves the packs and stamps the folder so it runs once per database). Each pack is named after its game, with its sidecar: launch address, developer, publisher, tags as genre, release, players, series, description; Flashpoint's logo and screenshot go to `roms/flash/.flashpoint-images` and become the cover, the snap and the Game info page (`public_artwork`, `game_info`: provider "Flashpoint"). Only the Flash platform is taken (not Shockwave, Unity, HTML5 or Java), and games Flashpoint marks extreme only with `--extreme`. Nothing is downloaded: a game whose files the copied install lacks is skipped.
- **Touch:** the game starts on the top screen, the bigger picture, and is played by finger there (the top Goodix); the second screen below opens on the touch pad, a laptop's, with Left and Right click, the arrows and Space beside it (`flash_pc` in `companion/keyboard.cpp`), the PC's keys a tap away (ABC). A finger is the mouse (`RETRO_DEVICE_POINTER`): **Direct** (`ruffle_touch=direct`, default) presses where the finger lands and drags with it; **Hover** (`ruffle_touch=hover`) moves the pointer with the finger and clicks on a short tap that stayed put, for games that aim or steer by the pointer. **Second screen → Keyboard** opens on a PC's keys below (the DOS layout: `F1-F12`, arrows, then **Mouse**, the laptop touch pad: slide to move, tap to click), through `Core::move_pad_mouse` as for DOS. **Holding the button** on the pad works as on a pad that clicks: press and keep the finger where it landed (about a fifth of a second, `press_frames`; the motor ticks and the pad lights) and the button is that finger's until it lifts, sliding or not (Bloons: press, slide to aim while the throw charges, lift). A finger that has slid never takes the button by resting, so aiming does not fire. Also: a second finger on the pad holds the left button while the first slides, a finger kept on **Left** or **Right** holds that button while another slides (the pad reads every finger of the panel for this, `View::fingers` from the player's second reader of `RGDS_TOUCH_DEV`), a tap and then a slide drags, and L or R held does the same from the shoulders. Both panels are touch screens: with the game below, the keyboard and touch pad drawn on the top screen are touched there (the top Goodix's touches go to the second screen in swap mode); a game left on the top screen is still played by finger there (the top Goodix, `aim_top` in `frontend/main.cpp`, for every touch game: Flash, ScummVM, light gun and mouse profiles), so the keys or the pad below and the game above are both at hand. The core draws a small pointer over the game while the pad or the stick moved it last (not while a finger is on the game, nor when the game hides its pointer).
- **Buttons** (core options, per game through the usual options file): the D-pad is the arrows, A Space, B Z, X X, Y C, L and R the mouse button (either hand holds it while the other is on the pad or the stick), L2 Shift, R2 the right button, Start Enter, Select P (`ruffle_btn_*`, `ruffle_dpad_*`: any letter, digit, arrow, Space, Enter, Shift, Ctrl, Alt, Esc, Tab, Backspace, `mouse`, `right click`, `none`). The mouse button is down while anything holds it (a finger on the picture, the pad, a shoulder), so a tap on the pad does not let go of a held R. The left stick (`ruffle_stick`, a stick to the player: `stick_buttons.hpp`) moves the pointer (`ruffle_cursor_speed`), or presses four keys: `arrows` or `wasd` (half a lean presses, a third lets go, a diagonal holds two). `auto` (default) is the arrows for a game Flashpoint tags racing, driving, platform, fighting, beat 'em up, shoot 'em up, runner, maze, snake or flying, else the pointer; a racing or driving game also drives on A (Up) and brakes on B (Down). **Per game:** any option without its `ruffle_` in the game's `.flashpoint` wins (`stick=wasd`, `touch=hover`, `btn_a=up`, `dpad_up=w`, `quality=low`); the importer writes all of Flashpoint's tags (`tags=`) for `auto`. The player has no menu for core options, so that file is where a game's controls are changed. Keys go to Flash as a desktop sends them: key down, the character typed, Enter/Backspace/arrows as text editing.
- **Saves:** Flash's own (SharedObjects) as `.sol` files under `userdata/emulators/rgds-play/saves/flash/<game>/<host>/...`, written beside and renamed; flushed when the game closes and on reset. Ruffle has no save states, so `flash` is in `NO_CHECKPOINTS`: Save/Load say the game keeps its own saves, Home and the switcher quit straight away, and the game menu has no Rewind tile (`rewind_tile_shown` in `src/launcher/main.cpp`, also for ScummVM and Game & Watch: Resume and Screenshot share the top row). Reset loads the movie again.
- **Picture:** on the handheld Ruffle draws on the player's own GLES 3 context (`SET_HW_RENDER`; `src/gl.rs`: wgpu adopts the current context with `new_external`, draws into a texture of the core's own, `src/target.rs`, and blits it into the player's framebuffer, scissored clears adding the stick's pointer), so a picture never comes back to the CPU. Play then blits that frame into the game panel's texture: the core's context shares the textures of the panel the game starts on (`gpu_panel` in `frontend/main.cpp`), and reads it back with `glReadPixels` only when the game was moved to the other panel. On the RG DS a context shared with the lower panel's fails (the top one's works, as for the Dreamcast), so a game started swapped is read back every picture: the first Flash build started on the lower panel and HappyWheels presented 27 of its 30 pictures a second with 100 ms stalls; Flash now starts on the top. A Flash game runs at its own frame rate (HappyWheels 30, killbox 15): Ruffle is ticked 1/60 s a frame and a frame with no new picture is a dupe, so a 30 fps game shows each picture for two refreshes. The first build read every picture back through wgpu (a texture-to-buffer copy, then a map): on Panfrost that copy alone cost 60-70 ms a picture while the GPU drew HappyWheels in 2-3 ms, so animations ran at 10-14 fps. Measured with `flash-headless` on the RG DS: HappyWheels 74 ms drawing and 14 ms reading back a picture before, 2.8 ms drawing after (1.9 ms a frame; 16.9 with a `glReadPixels` a picture). Where the player offers no context (a Mac's Play, play-shot) or wgpu can't use it, the core draws with a device of its own (Vulkan, Metal, else GLES through EGL with no window; `RGDS_FLASH_GPU=gl|vulkan`) and reads each picture back in one pass from the mapped buffer (the stage is opaque: no divide per pixel as in Ruffle's `capture_frame`); `RGDS_FLASH_SOFTWARE=1` forces that path. A frame Flash didn't change is a dupe; the stick's pointer moving costs a blit or a copy, not a render. `ruffle_quality` high (default)/low/medium/best. On the player's context the anti-aliasing is FXAA over the finished picture (`Fxaa` in `src/gl.rs`: one pass in place of the blit, edges found by luma above FXAA's contrast thresholds, about 2.6% of a HappyWheels picture changed), and the renderer never multisamples: a game that sets its own quality keeps it on the stage (text, its own checks) while the renderer is put back to Low. wgpu's GL MSAA on Panfrost cost 30 ms of drawing a frame in a HappyWheels level (1.1 ms without) and changed no pixel of the picture; drawing at twice the size and scaling down cost 138 ms. Low: no anti-aliasing at all. `RGDS_FLASH_MSAA=1` keeps Ruffle's MSAA on the context (measuring). Drawn on a device of its own (a Mac) the qualities are Ruffle's MSAA as they are; bitmaps are smoothed at every quality. Frames: the PC monitor. Audio: Ruffle's mixer at 44.1 kHz, 735 samples a frame. `RGDS_FLASH_LOG` sets the log filter (`info,ruffle_libretro=debug` shows the game's `trace` lines and, every 600 frames, the milliseconds a frame and the worst frame for the movie, its loaders, drawing, the read-back or blit and the sound). PanVK (DSCore's) loads but wgpu refuses it as a device, so Vulkan is not used on the handheld.
- **Speed, the mouse pick:** Ruffle looked for what is under the mouse after every update, three or more times a tick, and for an ActionScript 1/2 movie each look asked every clip on the stage for seven handler names (`onPress`, ...), making a string for each and searching the clip's children by name. In a level of Bloons (50 fps, some 50 bloons) that was three quarters of the tick: 19.4 ms a call on the RG DS, over its 16.7. `play/ruffle/patches/0001-mouse-pick-once-a-tick.patch` (applied to Ruffle's tag in `.cache/ruffle-src` by `tools/build_ruffle.py`, where Cargo.toml's `[patch]` takes every Ruffle crate from) looks once after each frame (and at once for a moved mouse or a button, as before), uses the interned names, asks an object and its prototypes once for all seven, and searches the children only when one's name starts with "on".
- **Speed, a movie's own quality:** the renderer never multisamples on the player's context (FXAA instead), but a movie that sets its quality itself (Swords and Sandals' GRAPHICS: HIGH) reached the renderer through the stage and turned 4x multisampling back on; its title, a drop shadow over the whole 682 x 428 scene redrawn every picture, took 74 ms a picture. `WgpuRenderBackend::pin_quality` (vendored renderer) keeps the renderer at the quality the core pins, the movie's own staying on the stage: 37 ms a picture (CPU 19, GPU 25 beside it). Also in the vendored renderer: each filter pass has buffers of its own (`filters::fresh_buffer`; every filter rewrote one shared uniform and vertex buffer per pass, the copy Panfrost flushes and waits on), a blur 10 pixels wide or more is worked out at half size and 32 or more at a quarter (`RGDS_FLASH_BLUR=full` for Ruffle's), the off-screen texture pool is kept between pictures (`RGDS_FLASH_POOL=frame` for Ruffle's), and `RGDS_FLASH_LOG=...,ruffle_render_wgpu=debug` names a movie's first sixty filters and their sizes. Ruffle's warnings are off by default (`error,ruffle_libretro=info`): Swords and Sandals wrote 800 "Unknown tag code: 253" lines a second.
- **Speed, what is left:** HappyWheels is its own ActionScript 3 (Box2D): 40 ms of script a 33 ms game frame in a level, 86% of it Ruffle's interpreter loop with no hot spot of Ruffle's own, so about 70% of full speed with every picture drawn. The cores at 1992 MHz instead of Balanced's 1608 gave 5%, PGO 3%.
- **Speed:** heavy games are CPU-bound on the RG DS. HappyWheels in a level (Happy Green Hills), per 60 Hz frame: ActionScript about 20 ms (Ruffle interprets it; Flash Player compiled it), Ruffle's drawing 3.5 ms, the GPU in parallel (about 17 draws, 5 chunks, 4,000 triangles a picture). Ruffle's wgpu renderer is vendored (`play/ruffle/vendor/ruffle_render_wgpu`, `[patch]` in Cargo.toml) with a ring of 16 chunk-buffer sets: Ruffle rewrote one transforms buffer and one vertex buffer for every chunk, and Panfrost copies buffers on the CPU, so each copy flushed the batch and waited for the GPU (drawing 10.1 -> 3.5 ms, frame 30.9 -> 24.6 ms; `RGDS_FLASH_RING=1` is the old behaviour). Built with fat LTO, one codegen unit and mimalloc (ActionScript 22.3 -> 19.6 ms); PGO (`tools/build_ruffle.py --pgo-generate/--pgo-use`) gave 3% more and is not used. Frame skip: the movie advances every call and a picture is left out while the core is behind real time, as many in a row as the drawing saved is worth (`skips_allowed` from the smoothed cost of a call's movie and a picture's drawing: none while both fit a frame, every second picture when the movie alone is late, up to three in four only when the drawing is the heavy part; a fixed three in four showed Bloons at 12 pictures a second); `RGDS_FLASH_FRAMESKIP=0` turns it off. HappyWheels: 40% of full speed before this work, 68% with the ring, 76% with frame skip (headless, GPU one picture behind). Measuring: the headless runner's `HEADLESS_WAIT=1` (glFinish each picture) or `=lag` (the previous picture's fence, like a swap chain), `HEADLESS_READ_UNTIL=N` (read back until frame N, the timing scripted taps need), `HEADLESS_DRAGS="FROM-TO:X,Y>X2,Y2"` (a finger held and slid: a held mouse button), `RGDS_FLASH_SKIP=render|present`, `RGDS_FLASH_RES`. Vulkan through PanVK works (`WGPU_ALLOW_UNDERLYING_NONCOMPLIANT_ADAPTER=1`, drawing 2 ms) but its GPU takes about 28 ms a picture.
- **Measuring on the handheld:** `python3 tools/build_ruffle.py --headless` builds `build/ruffle/flash-headless` (`examples/headless.rs`): a game through the core's libretro calls with no panels, on a GLES context of its own as Play makes it (`HEADLESS_READ=1` reads each picture back as Play does for a game on the other panel, `HEADLESS_SHOT=FILE.ppm` writes the last picture, `RGDS_FLASH_SOFTWARE=1` the read-back path; `HEADLESS_TAPS="FRAME:X,Y;..."` touches the picture at fractions of its size, `HEADLESS_HOLD="FRAME:ID"` holds a joypad button, `HEADLESS_SHOTS=F1,F2` writes shot-F.ppm, so a game can be timed past its title). Copy it and a game to `/tmp` and run it: it prints the frames, pictures and milliseconds a frame. A crash of any engine also leaves `userdata/logs/<engine>-crash.log`, which the next launch doesn't write over (`runtime/engine_log.py`).
- **Hooks:** `retro_rgds_wants_keyboard()` is 1 while a text field has focus (for the player to offer the keyboard; not used yet), `retro_rgds_flush_saves()` writes the saves now.

Built and tested on a Mac (`cd play/ruffle && cargo build --release`, Rust 1.99.1 from `rust-toolchain.toml`) with Ruffle's own test movies through `play-shot --drive`: a button pressed and released by touch at the right stage coordinates, Hover's slide (no click) and tap (one click), Start/A/B as Enter/Space/Z, on-screen keyboard keys, the touch pad moving and clicking, a SharedObject written in one run and read in the next, a Flashpoint-style zip and a curation zip each loading their second movie by web address, a gradient test drawn as expected (byte for byte the same with the one-pass read-back, 0.07 ms drawing and 0.48 ms reading back a picture on an M1), the stick as arrows on a racing-tagged movie (Up, then Up+Right, both let go; `stick X Y` in the drive). `cargo check --target aarch64-unknown-linux-gnu` is clean. For the handheld `tools/build_ruffle.py` cross-builds it on the Mac (Rust 1.99.1, zig as the linker, glibc 2.17; Buildroot's Rust 1.88 is too old for Ruffle 0.8.0) into `build/ruffle`, which `own_os_build.py` runs before the VM step and `package/libretro-ruffle` installs. Not yet on the handheld: GLES through surfaceless EGL on Panfrost, speed on the A55s and real games are unproven.

## RetroAchievements

Settings > Library > RetroAchievements: an On/Off switch per player (`achievements=1` in ui.ini) and the account.
Signing in runs `runtime/achievements.py login` once: the password goes to retroachievements.org on stdin and is
never kept; the token comes back into the private folder (`retroachievements.json`, plus `retroachievements.token`
in the "name, token" form DSCore reads). When the switch is on and a sign-in exists, `runtime/emulators.py` gives
the player `--achievements`, `--achievements-helper`, `--achievements-badges` and `--achievements-list`.

In the player, `app/achievements.cpp` runs rcheevos's rc_client in casual mode (softcore): sign-in with the token, the
game identified by its hash (the cartridge in memory for mGBA's systems, the file the core opened for libretro
cores), the set evaluated after every frame, its progress started over when a state is loaded. Memory is read
through `Core::achievement_memory`: rcheevos's GB/GBC/GBA layouts over mGBA's bus, and `rc_libretro` (RetroArch's
own mapping: the core's memory maps, else its system and save RAM) for every libretro core. Systems: everything the
player runs except the Pico, Amiga, Game & Watch, PICO-8 and ScummVM, which rcheevos cannot identify (CHD discs
are not hashed either).

The player has no TLS library: rcheevos's requests go to `achievements.py serve`, a helper process on two pipes
(one tab-separated request per line, answers framed by length; badge pictures saved straight into the badges
folder). Answers are handed to rcheevos on the game thread. A helper that dies answers "unreachable"; rcheevos keeps
an unlock and sends it again.

What the owner sees: a card that rises on the lower screen for an unlock (badge, title, description, points), the
set loaded ("3 / 40 achievements"), a mastery, and sign-in or connection trouble
(`frontend/achievement_toast.hpp`); and `achievements.tsv` in the game's player library folder, which Game info
lists. Not done: hardcore mode, leaderboards and challenge indicators on screen.

Tests: `build/play/host/play-achievement-tests` (a fake site: sign-in, set, unlock by memory, the list, a refused
token, the real pipes against a stand-in helper) and `tests/test_achievements.py`.

## Saves

Rules, enforced in `play/src/app/storage.cpp` and tested in `play/tests/play_tests.cpp` and `tests/test_play.py`:

- **Its own folder.** Everything lives under `userdata/emulators/rgds-play/` (`userdata/play/` for the standalone tools). The DS library, its saves, playtime, statistics and settings are never read or written; a test fills a fake `userdata/` with DS files and checks every byte and timestamp afterwards.
- **Atomic writes.** A battery save is written to `<name>.sav.writing`, fsynced, then renamed over the old file. A power cut or a lid sleep mid-write leaves the previous save. Writes happen on their own thread, at the moment mGBA reports that the game's write has settled.
- **Backups.** Each start keeps the previous save as `backups/<name>.sav.1`, `.2` and `.3`, skipping a rotation when nothing changed.
- **An unreadable save stops the start.** The game is not started over it, which would replace it.
- **Import, never move.** With no save of its own yet, the player looks next to the ROM (`<name>.sav`, `<name>.srm`) and in any `--save-source` folder (stock RetroArch's), copies the first one it finds, and leaves the original alone.
- **Signals save too.** SIGTERM, SIGINT and SIGHUP leave the loop through the same save path as quitting.

Layout: `<data>/saves/<system>/<rom name>.sav` and `<data>/saves/<system>/backups/`, where `<data>` is `userdata/emulators/rgds-play` under RG DS Core.

## Building and testing

```sh
python3 tools/build_play.py host --fetch   # libmgba (pinned) + rgds-play, play-shot, play-tests
python3 tools/build_play.py device         # aarch64 / glibc 2.17; needs `python3 tools/engine_toolchain.py --fetch` once
build/play/host/play-tests                 # unit tests
python3 -m unittest tests.test_play        # end to end on the test cartridge (needs Zig)
```

The test cartridge (`play/tests/testrom/`) is a 6 KB homebrew GBA game built with Zig: a title screen, twelve rooms, fades between them, a map screen on SELECT with a blinking marker, and an SRAM save. It carries no Nintendo logo or BIOS data.

`play-shot` runs a game headless from a script and writes both screens as one picture:

```sh
build/play/host/play-shot --rom GAME.gba --data /tmp/play --profiles play/profiles/gba \
  --fonts assets/fonts --script script.txt --out shots/
```

Script lines are `<frame> <buttons>` (held until the next line), `<frame> shot <name>`, `<frame> hudshot <name>` (the raw HUD layer), `<frame> capture`, `<frame> status` and `<frame> quit`. Captures finish before the next frame, so a run is the same every time; `--async` lets them race the game as on the handheld. `--hashes FILE` writes a hash of every frame's picture, `--state-hashes FILE` of the whole emulator state, and `--bench` times emulation and drawing per frame.

`rgds-play` is the windowed player: one window per panel when there are two displays, otherwise both panels stacked in one window. On the RG DS it reads the buttons straight from the pad's evdev device and grabs it, so nothing else receives or queues them while a game runs; elsewhere the keyboard and SDL game controllers work. Home, or Select+Start held for a second, saves and quits (`quit:` in its log says which). The game screen defaults to `--fit sharp`: the full panel width (640×427 on the RG DS), scaled up by a whole number on the GPU without smoothing and down to the panel with it, so pixels stay crisp and even; `--fit integer` keeps whole multiples (480×320), `--fit fill` is plain nearest-neighbour. These become Graphics options in the player's menu.

To hand-play on the handheld before the player is in a release:

```sh
python3 tools/build_play.py device
python3 tools/play_device.py deploy                      # to /mnt/mmc/rgds-play
python3 tools/play_device.py run "/mnt/mmc/Roms/GBA/Game.gba"
python3 tools/play_device.py log                         # status, stop
```

Everything lives in `/mnt/mmc/rgds-play` (the player, profiles, fonts, and saves in `data/`). The installed release is only read: the runner borrows its engine environment and its mixer-safe pause (`stop_outside_mixer`), pauses the launcher or the stock menu while the game runs, and resumes it when the player exits, however it exits. It refuses to start while another engine or benchmark is running. First hand-played on 23 October 2026: Mario Kart: Super Circuit on both panels, from the stock menu.

### Testing a profile over whole races

`tools/play_drive.py` races Super Circuit from a checkpoint with no one at the controls: `play-shot --drive` takes commands on stdin, and the script steers the player's kart along the trails the computer karts drive, printing every change of the HUD's registers and the split with a shot of both screens. Its `inputs.txt` replays the same race through the real player (`RGDS_PLAY_INPUT`, with `RGDS_PLAY_SHOTS`, `RGDS_PLAY_SHOT_EVERY` and `RGDS_PLAY_QUIT_AT`), on the Mac or on the handheld.
