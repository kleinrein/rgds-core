# Tanuki3DS for the RG DS

The Nintendo 3DS engine: our fork [kleinrein/Tanuki3DS-rgds](https://github.com/kleinrein/Tanuki3DS-rgds), branch
`rgds` (GPL-3.0), on [Tanuki3DS](https://github.com/burhanr13/Tanuki3DS) commit `879a1e7`, with SDL 3.2.24 and a
patched Mesa 25.2.8. It lives on the data partition, in `/data/rgds/engines/tanuki3ds`, because it needs about 380 MB
and the OS image has no room for it.

Still a spike. The fork mixes real changes with test hooks (the `SPIKE_*` variables, which the launch plan also uses
as settings):

- the renderer on its own thread, with command lists and vertex data copied when the game submits them;
- inline guest memory in the ARM JIT (`-DJIT_FASTMEM`);
- light tables cached by content, whole-tile updates of ETC1 atlases, per-draw GL state cached;
- JIT blocks that save nothing: `jit_enter` keeps the cpu, guest memory and the exit address in x27-x29 while guest code runs;
- Mesa's glthread on, for a third core (`map_unsynchronized_thread_safe` forced in Panfrost);
- the sound device opened at the mixer's 48 kHz, and a soft limiter instead of a hard clamp;
- a clean exit that skips teardown after flushing stdio (the teardown crashed under the renderer thread);
- each 3DS screen on its own panel, the RG DS's buttons and touchscreen read from evdev;
- a steady 60 Hz clock, with the sound queue held by a small resampling ratio;
- shader programs built on a helper thread in a shared context; a draw that needs an unbuilt one waits for it, because skipping such draws made backgrounds disappear;
- all JIT blocks side by side in one mapping, instead of a 16 KB mapping per block;
- RG DS Core's shared game menu without the SDL2 bridge (`src/rgds_bridge.c`): the files beside `RGDS_CONTROL_FILE`, the frame in `RGDS_OVERLAY_FILE`, the game held while `.blocked` exists;
- whole-machine save states (`src/savestate.c`, zstd, about 20 MB in Mario Kart 7), stored field by field with kernel objects and callbacks by name, so a state survives engine updates. The rules for keeping that true are at the top of the file. `state-check.sh` on the handheld proves two builds read each other's states, `state-diff.py` compares what they wrote. Build from a fresh folder or touch copied files: `limactl copy` keeps Mac times, and make then keeps an old object. Before installing, `grep -a` the binary: "this engine reads" must be there, "is not for this game and build" must not;
- the Graphics page's choices live: screen fit, second screen, RG DS Core's looks (`.dsd` presets adapted to GL 3.3 and fed the screen upright, as the 3DS screens lie on their side in their textures), and the 3DS lids as bezels (`rgds_bezel_draw`); the volume bar, fast-forward badge and FPS counter (`src/rgds_hud.cpp`, with copies of `src/platform/` headers);
- saves and loads on their own thread, so the menu's spinner goes on;
- a present only when the game has made a new picture (`SPIKE_PRESENT_ALL=1` presents every refresh), and textures rebuilt only when their bytes changed or more mip levels are asked for;
- ETC1 textures sent to the GPU as ETC2 blocks without decoding, each block flipped top to bottom (one step off in the about 2.6% of blocks that have no exact flip, `SPIKE_NOETC=1` decodes as before), and a tile table for the other formats' pixel order;
- frames skipped only when the renderer is 3 refreshes behind (`SPIKE_SKIP` in `run.sh`): at 2, a 30-picture game whose frame takes just over 33 ms lost every other picture, and 3D Land's levels showed 16-20 a second;
- shader sources with the same text share one program (2026-11-05, `ctremu.pt23`, staged, not installed, not run on the panels yet): Mario Kart 7's list held 911 vertex/fragment pairs, but its 617 fragment configurations are 255 texts and its 49 vertex shaders 15, so only 269 programs differ. Two thirds of the programs that still turned up as new late in a race were copies of one already built, each a 20 to 50 ms wait on the Mesa disk cache; the really new ones stay at about 250 ms each (the owner's slight freezes in races) and need another fix: a split link so a new fragment shader does not recompile the vertex shader, or a rewritten uber shader (`hostshaders/gpu.frag` is stale: no fog, procedural textures or shadows, and its uniform blocks no longer match `FragConfig`/`FragUniforms`). `SPIKE_NOTEXTSHARE=1` turns the sharing off. Old lists load as they are;
- an uber fragment shader as a stand-in while a program builds (2026-11-05, `ctremu.pt24`, staged, not installed, not yet run on the handheld's GPU): `shader_gen_uber_fs()` in `shadergen_fs.c` is one fragment shader that reads the whole `FragConfig` from a uniform block (binding 1) instead of having it baked in. A draw whose exact program is still building uses the uber program of the same vertex shader and switches when the exact one is ready, so a new material no longer freezes the picture for the 250 ms its link takes. Each vertex shader's uber program is built ahead of the list. Not used for shadow-map draws (the shadow sampler cannot share unit 0 with the plain one in one program): those wait as before. `SPIKE_NOUBER=1` waits always, `SPIKE_UBERONLY=1` draws everything with the uber shader (slow; for comparing pictures), the stats line ends `uber N` (draws that used it). `test_uber.c` here renders random configurations with both shaders in software GL and compares pixels (build line in its first comment block is the VM's: clang-19, the tree's `shadergen_fs.c.o` and `glad.c.o`, `-lEGL`): 2486 of 2500 within 2 levels of 255, the rest within 9 on lit surfaces (rounding). Change the generator and the uber body together and rerun it. `hostshaders/gpu.frag` is the old upstream uber shader and is no longer used;
- 2026-11-05 device results for the uber stand-in and the present path (`ctremu.pt26`, md5 9ec3a9e5, staged beside the installed engine, not installed):
  - the uber shader links on the Mali in about 1.0 s per vertex shader (once; the Mesa disk cache keeps it) and matches the exact shaders there too (`uber-gpu.sh` on the handheld runs `test_uber` on the render node, no panels: 150 of 150);
  - it is slow: one 400x240 layer costs 24 ms against 0.3 ms (`TEST_UBER_COST=1`), and a frame drawn wholly with it (`SPIKE_UBERONLY=1`) runs into the kernel's 500 ms GPU job timeout, with garbage pictures and page faults in dmesg. So `SPIKE_UBERONLY` is not a usable comparison mode, and the stand-in is only used while at most two programs are waiting (`g_pb.nhot <= 2`); a burst waits for the exact programs as before. Uber programs are built ahead of exact ones;
  - a scripted Mario Kart 7 race with every exact link made to take 250 ms (`SPIKE_NOPROGLIST=1 SPIKE_SLOWLINK=250`, 80 s): waiting for programs 2633 ms with `SPIKE_NOUBER=1` against 329 ms with the stand-in (the rest is the first uber link), windows with a gap over 100 ms 10 against 2, about 425 draws used the stand-in, no GPU timeouts;
  - **the blinking on scripted runs was the direct present path** (display transfers writing straight into a present set): the top panel showed the bottom screen's picture for single frames about once a second, in the installed engine too (13 of 335 frames captured with `SPIKE_SHOT_EVERY=7`, 0 of 338 with the copy path; scan with brightness of the top captures). Not other launches fighting over the panels, as noted on 2026-11-04. The cause is not found. The copy path is the default from pt25 on (`SPIKE_PRESENT_DIRECT=1` for the old one); it costs about 0.9 ms of renderer time a frame in that race (99.5% of frames drawn against 99.9%);
  - save-state check against the installed engine both ways: loaded, 60 fps, all chunks the same;
  - installed 2026-11-05 15:12 UTC on the owner's OK as `ctremu` (md5 9ec3a9e5); the engine before it is `ctremu.installed-1105-1512` (4a860b6b, pt21). It also carries the 3D Land present cadence (pt22b), not yet judged by eye; `SPIKE_NOCADENCE=1` turns that off;
- lists per game in the game's home, `shaders/<rom>.list` (built ahead from the start of a run) and `jit/<rom>.list` (compiled ahead in spare frame time, once code with the same hash is in memory). Bump `PROGLIST_VERSION` in `renderer_gl.c` when the shader generators change;
- ETC1 and ETC1A4 textures keep a copy of the bytes they were built from (`shadow`, 8 MB per texture and 96 MB in all at most): when the game writes into one, only the 8x8 tiles whose bytes differ are decoded and uploaded (`tex_diff_update`), instead of decoding the whole atlas again. NSMB2 rebuilt a 1-megapixel ETC1A4 atlas 10-16 times a half second, 23 ms each, in the owner's hand play. `SPIKE_NOSHADOW=1` turns it off, `SPIKE_TEXLOG=1` logs every full rebuild with its reason;
- a present thread: SDL's KMS swap waits for that panel's previous flip, so two panels cost the renderer thread two vblank waits a frame (11-12 ms of its 16 in NSMB2); now the display transfers write into one of eight present sets and the present thread draws the panels and swaps from there, while the renderer goes on;
- a GL state cache on the draw path (`gls_*` setters in `renderer_gl.c`): every GL call is marshalled to Mesa's driver thread, about 39 a draw, most setting what was already set; the setters skip those, 7.6 calls a draw remain, and anything else touching that state invalidates the cache. Mario Kart races went from 88% to 96.5% of frames drawn, the NSMB2 map from 46 to 60 fps. `SPIKE_NOGLCACHE=1` turns it off; the stats line's `glcalls a/b` is calls sent of calls asked. With `GL_ARB_vertex_attrib_binding` (Mesa hides it under the 3.3 version override; `MESA_EXTENSION_OVERRIDE=+GL_ARB_vertex_attrib_binding` shows it, `SPIKE_ATTRIBBINDING=1` uses it) the vertex data's place is one `glBindVertexBuffer` per buffer a draw instead of one `glVertexAttribPointer` per attribute;
- the index range kept through Mesa's glthread (a Mesa patch in `build-mesa.sh`): glthread packs every draw from a buffer without the start and end that `glDrawRangeElementsBaseVertex` gives it, and the driver thread then scans each draw's indices for the vertex range Panfrost's vertex job needs, 14% of that thread in a Mario Kart 7 race. Ranged draws now keep their range. Measured 2026-11-03 at the same heat (the GPU capped at 600 MHz by another session's experiment during the two patched runs, 800 for the two before): race frames drawn 98.2-98.6% before, 99.5% after; the driver thread from 51% to 39% of a core, the renderer thread's frame from 13.3 to 11.5 ms. Without the client wait on the present set's fence on top (now the default; `SPIKE_PSETWAIT=1` restores it): 99.8%, the driver thread at 34%, the renderer at 10.2 ms. In the owner's hands the difference is far larger: through the launcher that wait costs 5.5 ms of every frame (2.5 on a bare test launch, the reason not found) and the owner's own runs drew 78% of frames with it against 97.5% without. The blinking reported the same morning, with either build, was always another launch fighting over the panels (a test run, another session's game or benchmark): never take the panels while the owner is at the device. The scripted test launches themselves (`hold3ds.sh`, the launcher killed under a bind instead of handing the displays over) blink on the panels on the 2026-11-04 image while the same engine launched by hand does not: a test run's numbers still hold, its picture does not, and whatever the killed launcher leaves behind on the displays is not understood yet. Ten minutes of Grand Prix on a copy of the owner's data with both (the chip at its 70 °C trip from minute four, the CPU held at 1416-1608 MHz, the GPU at 600 MHz, harsher than the owner's Performance mode): 99.6% of frames drawn over the run, 99.2-99.8% in every two-minute slice after the first, against 86-88% in the owner's throttled minutes before; what is still lost sits in race starts and first visits of a track (shader builds, texture creates). `MESA_DIR=<folder>` in `run.sh` runs another Mesa folder beside `lib2` (the patched build was tried as `lib2r` before replacing `lib2`'s gallium library);
- the vertex shader's float uniform FIFO replayed by a loop of its own on the renderer thread (most of a command list's words in Mario Kart 7 are uniform data, three or four per vec4, and each went through the 300-way register switch; `SPIKE_NOUNIFORMRUN=1` restores that), built 2026-11-04 as `ctremu.pt20`: a race at the same heat drew the same frames (99.7% against 99.8%) with the renderer thread at 46% of a core instead of 50%, so it is a small saving of heat, not frames; kept beside the installed engine, not installed;
- vertex layouts the driver takes as they are: Panfrost has no vertex format for three 16-bit components, and wants each attribute and the stride aligned to the component size; for any other layout Mesa copies the draw's vertices into one it can use, on its driver thread, for every draw, and scans the indices for the vertex range first (together a quarter of that thread in Mario Kart 7, whose models use 16-bit positions). The main thread, which copies each draw's vertices out of guest memory anyway, now lays such buffers out as it copies (`gpu_vbo_layout` in `gpu.c`, the same rule on both threads): short3 becomes short4 with w = 1, as the PICA fills a missing component, and everything is aligned (`relaid` in the stats counts those draws);
- waits that sleep: the renderer thread spun on `sched_yield` while waiting for commands and the main thread while waiting for presents, two cores busy with nothing, which heats the chip towards its 70 °C trip (the CPU then drops to 1.6 GHz). Each side now spins briefly and sleeps on a futex, woken only when it said it was asleep (`SPIKE_SPINWAIT=1` restores the spinning);
- the internal resolution per game: `RGDS_3DS_SCALE=1..3` from the launcher (the game's `play.ini` `scale`, the Graphics page's "Internal resolution" row for 3DS games, saved by the menu's `play-scale:<n>` and taken at the next launch, as the framebuffers are sized at start; until 2026-11-03 afternoon the menu's request reader dropped that request unread, so the choice never reached `play.ini`, now covered by a test through the request file). Measured 2026-11-03 on the installed engine: 3D Land at 2x keeps its 30 fps (0 lost in a 150 s attract demo, renderer 8 ms a refresh) with visibly cleaner edges; NSMB2 at 2x loses a quarter of its frames (levels 83%, the map 62%, renderer 12-19 ms), so 2x is for 3D Land and other 30 fps games, not for NSMB2 or Mario Kart 7;
- every run's numbers in `logs/<time>-<rom>.log` in the game's home (`.local/share/Tanuki3DS/logs`), the newest 30 kept, because the launcher's `rgds-play.log` holds only the tail of one run. The stats line ends with `texdiff N tiles N ms N new/stale/rehash a/b/c`: tile updates, and full rebuilds by reason.

Super Mario 3D Land is a 30 fps game by design (the game itself hands over one new image per two refreshes; GameFAQs and Nintendo Life threads agree, and the engine's `guest` count shows 15 transfers per 30 refreshes even under fast-forward with the renderer idle), so 60 fps is not reachable without a game patch. What the engine can affect is how steady that 30 is: in levels the main thread takes 10-15 ms per refresh with single refreshes at 22-32 ms (log of 2026-11-04 12:15 local), the renderer only 7-9 ms, so the lever is CPU emulation, not drawing. `headless-3dl.sh SECS` in `/data/rgds/3ds-spike` profiles the main thread in a level on the userdata copy without the panels (SDL offscreen driver, EGL surfaceless; untested), from a copy of the owner's checkpoint; the samples land in `tanuki-run/h3-NAME.psamp` (the in-engine `SPIKE_PROF_MAIN` profiler crashes in its stack walker on JIT frames; `psamp` samples the program counter from outside). `headless-3dl.sh NAME SECS` with `BIN=ctremu.ptN` runs a staged build.

Main thread of 3D Land in a level (2026-11-04, 60 s of samples): 48% generated JIT code, 21% the dispatch of blocks through C (`get_jitblock`, `arm_exec_jit`, `jit_enter`: every `bx lr` and every pointer call left the generated code), 10% the GPU command front end (`gw_front_write`/`walk`/`snap_draw`), 10% memcpy (draw data copied out of guest memory), 4% the DSP mixer, 3.5% kernel. The JIT already links direct branches; indirect ones now go through an inline cache (`jit.h` `g_jit_ic`, 65536 entries keyed by pc and the block attributes, looked up in the generated epilogue of a block whose END_RET carries op1 = 1, filled by `arm_exec_jit`, emptied when any block is destroyed). A block that raised an exception, wrote cp15 or switched modes keeps returning to C, since the kernel applies the thread switch to the register file there: the first build without that rule crashed in the TLS read of the next block. Dispatches through C went from about 15000 a refresh to 310 (200 of them system calls), the main thread from 11.9 to 10.7 ms a refresh (headless A/B, same checkpoint); 4096 entries only reached 11.4 (1750 conflict misses a refresh, and `pc >> 1` wasted half the slots on ARM code). The stats line ends with `disp N/C/E`: blocks entered from C per refresh, of which C had to be entered, and conflict evictions. `SPIKE_NOIC=1` compiles blocks without the lookup. Build pt21 (md5 4a860b6b) was state-checked both ways against pt17 on 2026-11-04 12:09-12:11 UTC (each loaded the other's Mario Kart state, ran at 60 fps, wrote it back with all 14 chunks identical) and installed as the engine at 12:13 UTC on the owner's go; the previous binary is `ctremu.installed-1104-1213` (1f1ad3c7).

What that leaves: the heavy refresh of each 3D Land frame (the game does a frame's logic in one refresh and idles the next) still takes about 21 ms against a 16.7 ms budget, so the picture is still paced unevenly; making the main thread 25% faster would need JIT code generation work. The practical lever is presentation, now written as pt22 (md5 732e6501, staged, not installed): the present thread keeps a running average of the gaps between the renderer's hand-offs, and while they come about two refreshes apart (26-42 ms), an image that is ready before the first refresh after the last top-panel flip is held until 23 ms after that flip, so its swap lands on the second refresh (`present_cadence` in main.c; `SPIKE_NOCADENCE=1` turns it off). Costs up to one refresh of latency in such a game, nothing in a 60 fps one. The stats line now shows `pt presented/dropped/held` and `flips a/b/c`, the gaps between top-panel flips of 1, 2 and 3+ refreshes: a steady 30 fps game should read `flips 0/15/0` per half-second window. `land-run.sh NAME BIN SECS` runs 3D Land on the panels from a fixed copy of the owner's checkpoint (needs a window from the owner).
Measured 2026-11-04 12:20-12:23 UTC (land-off / land-on in tanuki-run): with the cadence off 9 of 101 windows were perfect (`flips 0/15/0`), the rest `2/14/0`; with it on 31 of 86. The imperfect windows are the ones where the game delivered 16 images in 30 refreshes: 3D Land is not a fixed 30, it makes about 32 images a second, and 16 cannot all stay up two refreshes in 30. The first build capped the hold at 20 ms, so an image arriving right after a flip was not held; pt22b (md5 d4165017, staged) holds up to 34 ms, which lets the renderer replace that extra image with the next one, so one image a second is skipped instead of two shown for a single refresh. Not measured yet, and whether a skipped image a second beats the 1/3 pattern is for the owner's eyes.

A new Mesa build empties the shader cache (`/data/rgds/cache/mesa-spike` is keyed by the driver), and the first launch of each game after it links every program again at about 270 ms each. A game's list is built in the background from the start of a run, one program at a time, so a level that needs many programs at once before the list has reached them waits for them: Super Mario 3D Land froze for 25 s on its first level load after the 2026-11-04 Mesa change (93 links, 15 s of waiting in one frame), Mario Kart 7 lost 1.7 s at its first race start. The second launch is fine. After a Mesa change, let each game sit on its title screen for a minute before playing, or warm the lists first; a warm step in the install script is the proper fix and not written yet.

Build in the Lima VM (`rgds-image`), under `~/3ds-spike`. Files copied into the VM with `limactl copy` keep their Mac mtime, so a copied file older than its object is not rebuilt: touch what you copy, or `make -B`.

    sh build-tanuki.sh   # SDL3 and the fork's rgds branch (TANUKI_REF=<branch or commit> for another, TANUKI_KEEP=1 to build the clone as it is)
    sh build-mesa.sh     # Mesa with Panfrost's buffer cache patched
    sh bundle-tanuki.sh  # tanuki-bundle.tar

Settings the handheld needs are in `ctremu.ini`, copied to the game's home on first launch.

The engine folder holds Mesa twice: `lib` is Ubuntu's, `lib2` is our build from `build-mesa.sh` (the Panfrost buffer cache keeps its buffers mapped and skips the label and madvise ioctls per reuse, and the `map_unsynchronized_thread_safe` cap is set so Mesa's glthread starts, which takes the driver's per-draw work off the renderer thread; the system `libLLVM.so.19.1` sits beside it). `run.sh` puts `lib2` first; `MESA_STOCK=1` runs Ubuntu's, `NO_GLTHREAD=1` leaves the driver thread off. Sorted out 2026-11-02 by sampling the renderer thread: the Ubuntu EGL library loads the gallium file by Ubuntu's file name, so a lone gallium library in a folder of its own (`lib3`) only ever loaded next to our own EGL library (`lib2`), and `lib2` itself held a day-older gallium build without the cap. `lib2` now carries the build with it and `lib3` is retired; check with `ls /proc/<pid>/task/*/comm` for `ctremu:gl0` threads.

Test and measurement switches: `SPIKE_PROF_WORKER=1` or `SPIKE_PROF_GL=1` with `SPIKE_PROF_FROM=<frame>` sample the renderer thread or the first driver thread (`SPIKE_PROF_US` between samples) into `prof.txt` in the game's home, written at quit or on SIGTERM; `SPIKE_SKIPDRAW=1|2|4` leaves all, the lit, or the unlit draws out; `SPIKE_DIFFCHECK=1` verifies the texture shadows after each tile diff; `SPIKE_PRESENT_COPY=1` copies the screens into a present set instead of the display transfers writing it; `SPIKE_NOPRESENTTHREAD=1` presents from the renderer thread as before; `SPIKE_GPUTIME=1` turns on GPU timestamp queries, whose `gpu` figure in the stats line is the GPU timeline per frame (polling them costs the renderer thread 12%, so they are off by default), `pt a/b` frames presented and dropped by the present thread.
