# Tanuki3DS for the RG DS

The Nintendo 3DS engine: our fork [kleinrein/Tanuki3DS-rgds](https://github.com/kleinrein/Tanuki3DS-rgds), branch
`rgds` (GPL-3.0), on [Tanuki3DS](https://github.com/burhanr13/Tanuki3DS) commit `879a1e7`, with SDL 3.2.24 and a
patched Mesa 25.2.8. It lives on the data partition, in `/data/rgds/engines/tanuki3ds`, because it needs about 380 MB
and the OS image has no room for it.

Still a spike. The fork mixes real changes with test hooks (the `SPIKE_*` variables, which the launch plan also uses
as settings):

- the renderer on its own thread, with command lists and vertex data copied when the game submits them;
- inline guest memory in the ARM JIT (`-DJIT_FASTMEM`);
- light tables cached by content, whole-tile updates of ETC1 atlases, per-draw GL state cached;
- JIT blocks that save nothing: `jit_enter` keeps the cpu, guest memory and the exit address in x27-x29 while guest code runs;
- Mesa's glthread on, for a third core (`map_unsynchronized_thread_safe` forced in Panfrost);
- the sound device opened at the mixer's 48 kHz, and a soft limiter instead of a hard clamp;
- a clean exit that skips teardown after flushing stdio (the teardown crashed under the renderer thread);
- each 3DS screen on its own panel, the RG DS's buttons and touchscreen read from evdev;
- a steady 60 Hz clock, with the sound queue held by a small resampling ratio;
- shader programs built on a helper thread in a shared context; a draw that needs an unbuilt one waits for it, because skipping such draws made backgrounds disappear;
- all JIT blocks side by side in one mapping, instead of a 16 KB mapping per block;
- RG DS Core's shared game menu without the SDL2 bridge (`src/rgds_bridge.c`): the files beside `RGDS_CONTROL_FILE`, the frame in `RGDS_OVERLAY_FILE`, the game held while `.blocked` exists;
- whole-machine save states (`src/savestate.c`, zstd, about 20 MB in Mario Kart 7), stored field by field with kernel objects and callbacks by name, so a state survives engine updates. The rules for keeping that true are at the top of the file. `state-check.sh` on the handheld proves two builds read each other's states, `state-diff.py` compares what they wrote. Build from a fresh folder or touch copied files: `limactl copy` keeps Mac times, and make then keeps an old object. Before installing, `grep -a` the binary: "this engine reads" must be there, "is not for this game and build" must not;
- the Graphics page's choices live: screen fit, second screen, RG DS Core's looks (`.dsd` presets adapted to GL 3.3 and fed the screen upright, as the 3DS screens lie on their side in their textures), and the 3DS lids as bezels (`rgds_bezel_draw`); the volume bar, fast-forward badge and FPS counter (`src/rgds_hud.cpp`, with copies of `src/platform/` headers);
- saves and loads on their own thread, so the menu's spinner goes on;
- a present only when the game has made a new picture (`SPIKE_PRESENT_ALL=1` presents every refresh), and textures rebuilt only when their bytes changed or more mip levels are asked for;
- ETC1 textures sent to the GPU as ETC2 blocks without decoding, each block flipped top to bottom (one step off in the about 2.6% of blocks that have no exact flip, `SPIKE_NOETC=1` decodes as before), and a tile table for the other formats' pixel order;
- frames skipped only when the renderer is 3 refreshes behind (`SPIKE_SKIP` in `run.sh`): at 2, a 30-picture game whose frame takes just over 33 ms lost every other picture, and 3D Land's levels showed 16-20 a second;
- lists per game in the game's home, `shaders/<rom>.list` (built ahead from the start of a run) and `jit/<rom>.list` (compiled ahead in spare frame time, once code with the same hash is in memory). Bump `PROGLIST_VERSION` in `renderer_gl.c` when the shader generators change;
- ETC1 and ETC1A4 textures keep a copy of the bytes they were built from (`shadow`, 8 MB per texture and 96 MB in all at most): when the game writes into one, only the 8x8 tiles whose bytes differ are decoded and uploaded (`tex_diff_update`), instead of decoding the whole atlas again. NSMB2 rebuilt a 1-megapixel ETC1A4 atlas 10-16 times a half second, 23 ms each, in the owner's hand play. `SPIKE_NOSHADOW=1` turns it off, `SPIKE_TEXLOG=1` logs every full rebuild with its reason;
- a present thread: SDL's KMS swap waits for that panel's previous flip, so two panels cost the renderer thread two vblank waits a frame (11-12 ms of its 16 in NSMB2); now the display transfers write into one of eight present sets and the present thread draws the panels and swaps from there, while the renderer goes on;
- a GL state cache on the draw path (`gls_*` setters in `renderer_gl.c`): every GL call is marshalled to Mesa's driver thread, about 39 a draw, most setting what was already set; the setters skip those, 7.6 calls a draw remain, and anything else touching that state invalidates the cache. Mario Kart races went from 88% to 96.5% of frames drawn, the NSMB2 map from 46 to 60 fps. `SPIKE_NOGLCACHE=1` turns it off; the stats line's `glcalls a/b` is calls sent of calls asked. With `GL_ARB_vertex_attrib_binding` (Mesa hides it under the 3.3 version override; `MESA_EXTENSION_OVERRIDE=+GL_ARB_vertex_attrib_binding` shows it, `SPIKE_ATTRIBBINDING=1` uses it) the vertex data's place is one `glBindVertexBuffer` per buffer a draw instead of one `glVertexAttribPointer` per attribute;
- the index range kept through Mesa's glthread (a Mesa patch in `build-mesa.sh`): glthread packs every draw from a buffer without the start and end that `glDrawRangeElementsBaseVertex` gives it, and the driver thread then scans each draw's indices for the vertex range Panfrost's vertex job needs, 14% of that thread in a Mario Kart 7 race. Ranged draws now keep their range. Measured 2026-11-03 at the same heat (the GPU capped at 600 MHz by another session's experiment during the two patched runs, 800 for the two before): race frames drawn 98.2-98.6% before, 99.5% after; the driver thread from 51% to 39% of a core, the renderer thread's frame from 13.3 to 11.5 ms. Without the client wait on the present set's fence on top (a glthread sync point, now off by default; `SPIKE_PSETWAIT=1` restores it): 99.8%, the driver thread at 34%, the renderer at 10.2 ms. Ten minutes of Grand Prix on a copy of the owner's data with both (the chip at its 70 °C trip from minute four, the CPU held at 1416-1608 MHz, the GPU at 600 MHz, harsher than the owner's Performance mode): 99.6% of frames drawn over the run, 99.2-99.8% in every two-minute slice after the first, against 86-88% in the owner's throttled minutes before; what is still lost sits in race starts and first visits of a track (shader builds, texture creates). `MESA_DIR=<folder>` in `run.sh` runs another Mesa folder beside `lib2` (the patched build was tried as `lib2r` before replacing `lib2`'s gallium library);
- vertex layouts the driver takes as they are: Panfrost has no vertex format for three 16-bit components, and wants each attribute and the stride aligned to the component size; for any other layout Mesa copies the draw's vertices into one it can use, on its driver thread, for every draw, and scans the indices for the vertex range first (together a quarter of that thread in Mario Kart 7, whose models use 16-bit positions). The main thread, which copies each draw's vertices out of guest memory anyway, now lays such buffers out as it copies (`gpu_vbo_layout` in `gpu.c`, the same rule on both threads): short3 becomes short4 with w = 1, as the PICA fills a missing component, and everything is aligned (`relaid` in the stats counts those draws);
- waits that sleep: the renderer thread spun on `sched_yield` while waiting for commands and the main thread while waiting for presents, two cores busy with nothing, which heats the chip towards its 70 °C trip (the CPU then drops to 1.6 GHz). Each side now spins briefly and sleeps on a futex, woken only when it said it was asleep (`SPIKE_SPINWAIT=1` restores the spinning);
- the internal resolution per game: `RGDS_3DS_SCALE=1..3` from the launcher (the game's `play.ini` `scale`, the Graphics page's "Internal resolution" row for 3DS games, saved by the menu's `play-scale:<n>` and taken at the next launch, as the framebuffers are sized at start; until 2026-11-03 afternoon the menu's request reader dropped that request unread, so the choice never reached `play.ini`, now covered by a test through the request file). Measured 2026-11-03 on the installed engine: 3D Land at 2x keeps its 30 fps (0 lost in a 150 s attract demo, renderer 8 ms a refresh) with visibly cleaner edges; NSMB2 at 2x loses a quarter of its frames (levels 83%, the map 62%, renderer 12-19 ms), so 2x is for 3D Land and other 30 fps games, not for NSMB2 or Mario Kart 7;
- every run's numbers in `logs/<time>-<rom>.log` in the game's home (`.local/share/Tanuki3DS/logs`), the newest 30 kept, because the launcher's `rgds-play.log` holds only the tail of one run. The stats line ends with `texdiff N tiles N ms N new/stale/rehash a/b/c`: tile updates, and full rebuilds by reason.

Build in the Lima VM (`rgds-image`), under `~/3ds-spike`. Files copied into the VM with `limactl copy` keep their Mac mtime, so a copied file older than its object is not rebuilt: touch what you copy, or `make -B`.

    sh build-tanuki.sh   # SDL3 and the fork's rgds branch (TANUKI_REF=<branch or commit> for another, TANUKI_KEEP=1 to build the clone as it is)
    sh build-mesa.sh     # Mesa with Panfrost's buffer cache patched
    sh bundle-tanuki.sh  # tanuki-bundle.tar

Settings the handheld needs are in `ctremu.ini`, copied to the game's home on first launch.

The engine folder holds Mesa twice: `lib` is Ubuntu's, `lib2` is our build from `build-mesa.sh` (the Panfrost buffer cache keeps its buffers mapped and skips the label and madvise ioctls per reuse, and the `map_unsynchronized_thread_safe` cap is set so Mesa's glthread starts, which takes the driver's per-draw work off the renderer thread; the system `libLLVM.so.19.1` sits beside it). `run.sh` puts `lib2` first; `MESA_STOCK=1` runs Ubuntu's, `NO_GLTHREAD=1` leaves the driver thread off. Sorted out 2026-11-02 by sampling the renderer thread: the Ubuntu EGL library loads the gallium file by Ubuntu's file name, so a lone gallium library in a folder of its own (`lib3`) only ever loaded next to our own EGL library (`lib2`), and `lib2` itself held a day-older gallium build without the cap. `lib2` now carries the build with it and `lib3` is retired; check with `ls /proc/<pid>/task/*/comm` for `ctremu:gl0` threads.

Test and measurement switches: `SPIKE_PROF_WORKER=1` or `SPIKE_PROF_GL=1` with `SPIKE_PROF_FROM=<frame>` sample the renderer thread or the first driver thread (`SPIKE_PROF_US` between samples) into `prof.txt` in the game's home, written at quit or on SIGTERM; `SPIKE_SKIPDRAW=1|2|4` leaves all, the lit, or the unlit draws out; `SPIKE_DIFFCHECK=1` verifies the texture shadows after each tile diff; `SPIKE_PRESENT_COPY=1` copies the screens into a present set instead of the display transfers writing it; `SPIKE_NOPRESENTTHREAD=1` presents from the renderer thread as before; `SPIKE_GPUTIME=1` turns on GPU timestamp queries, whose `gpu` figure in the stats line is the GPU timeline per frame (polling them costs the renderer thread 12%, so they are off by default), `pt a/b` frames presented and dropped by the present thread.
